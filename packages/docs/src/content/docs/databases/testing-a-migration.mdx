This is the strongest single reason to use a sandbox. A migration is the one change you cannot
undo and cannot meaningfully test against an empty database, and this gives you a copy of real
structure and real volume that you are allowed to destroy.

## The loop

```bash
sandboxr db fork       # copy the source into a scratch database
sandboxr db pending    # what this branch would run
sandboxr db migrate    # run it
sandboxr db diff       # what actually changed
sandboxr db reset      # throw it away and start again
```

<Aside type="note" title="This works with no sandbox at all">
`sandboxr db` needs no container, no router and no DNS. It is useful on its own, on a machine
where you have never run `sandboxr init`. A sandbox does the same thing at boot, against its
own internal database.
</Aside>

<Aside type="caution" title="Derived commands">
The safety properties on this page are contract. The `db` subcommand names are derived from
the tool sandboxr generalises and are not pinned anywhere yet. See
[what is built](/reference/status/).
</Aside>

## Why it is safe

<Mermaid
  caption="Nothing destructive ever touches the left-hand box."
  chart={`

  scratch[("Scratch copy")]
  sbx[("A sandbox's<br/>own database")]
  src -->|"read only, always"| scratch
  src -->|"read only, always"| sbx
  scratch -->|"migrate, diff, reset,<br/>drop, anything"| scratch
  sbx -->|"migrate, diff, reset,<br/>drop, anything"| sbx

**The source is only ever read.** Every destructive operation targets a copy — the scratch
database for `sandboxr db`, or the database inside a sandbox. That separation is the whole
point: it is what makes it reasonable to run a migration you are not sure about.

If it were not true, the first person to typo a `DROP TABLE` while testing would lose their own
development database, and nobody would use the tool again.

## Step by step

<Steps>

1. **Fork.**

   ```bash
   sandboxr db fork
   ```

   Produces a copy of the source at the version the config declares and creates the app user.
   It then takes a **schema baseline**, which is the thing `diff` compares against.

   If the source's migration bookkeeping has rows left unfinished by an earlier attempt, the
   project's runner will refuse to proceed — correctly. sandboxr does not repair that, because
   repairing it means reimplementing the project's migration logic.
   [What to do](/databases/mysql/#stuck-migration-bookkeeping-is-the-projects-problem-deliberately).

2. **See what is pending.**

   ```bash
   sandboxr db pending
   ```

   ```
   3 pending migrations:
     20240612-1030-add-orders-index.sql
     20240614-0915-add-orders-status.sql
     20240615-1120-backfill-orders-status.sql
   ```

   This set is computed from **this worktree's** migration directory, so two branches
   legitimately report different counts. That is a feature: it is exactly the "what would this
   branch do" question.

3. **Run it.**

   ```bash
   sandboxr db migrate
   ```

   This shells out to the project's own migration command. sandboxr does not order, apply or
   track migrations itself; it may read the runner's state to show progress, but the program
   that runs is the project's.

   A failure here is not a problem. It is information.

4. **See what changed.**

   ```bash
   sandboxr db diff
   ```

   A structure-only diff of the baseline against the current schema. Columns added, indexes
   created, types changed — and, after a failure, exactly how far it got.

5. **Start again.**

   ```bash
   sandboxr db reset
   ```

   Back to a clean restore, baseline re-taken, fixtures re-applied. On a file-based driver this
   is close to instant; on MySQL it is a restore.

</Steps>

## After a failed migration, the diff is the point

DDL is not transactional in every engine. A migration can fail with earlier statements already
committed, leaving a schema that is neither the old one nor the new one.

`sandboxr db diff` answers "what did that actually change?" — and it can only answer it because
**the baseline was not overwritten by the failed attempt.**

<Aside type="danger" title="Why the baseline is only re-taken after a success">
If the baseline were re-snapshotted on every attempt, a failed run would replace it with the
half-migrated state. The next `diff` would then report **no change** — at precisely the moment
the question matters most, and in a way that reads as reassurance rather than as a missing
answer.

The baseline is re-taken after a successful migration, or when `fork`/`reset` starts from a
clean restore. Never after a failure.
</Aside>

So the useful sequence after a failure is:

```bash
sandboxr db diff        # how far did it get?
sandboxr db shell       # look at the actual state
# fix the migration file in your editor
sandboxr db reset       # clean slate
sandboxr db migrate     # try again
```

## Inside a sandbox

A sandbox does all of the above at boot, against its own database, and then **keeps running
even if the migration failed**. That is deliberate: the sandbox is where you inspect the
failure.

```bash
sandboxr list                      # shows `degraded`
sandboxr logs feat-123 db-init     # the migration output
sandboxr db diff                   # what landed
sandboxr shell                     # or poke around directly
```

Re-running a migration inside a sandbox after editing the file is the same command:

```bash
sandboxr db migrate
```

And when the database is no longer in a state you trust:

```bash
sandboxr db reset
```

## What this does not test

Be honest with yourself about the limits.

- **It does not test production data volume**, unless your seed has it. A migration that takes
  four seconds on a fork of a laptop database can take forty minutes on production. If runtime
  matters, measure against a dump with real row counts.
- **It does not test concurrent load.** A migration that takes a table lock behaves very
  differently with traffic on it.
- **It does not test the deploy ordering.** If your project ships schema changes and the code
  that uses them in separate releases, a sandbox tells you the migration works — not that the
  *sequence* is safe.
- **It does not test rollback**, because there usually is no rollback. If your project's answer
  to a bad migration is "write a new one", a sandbox is where you write and test that one too.

## Practical habits

| Habit | Why |
|---|---|
| `db pending` before `db migrate`, every time | Confirms you are running what you think you are running. |
| `db diff` after every run, including successes | The diff is also a review artefact: paste it into the pull request. |
| `db reset` between attempts, not `db migrate` twice | A second run on a half-migrated schema tests a state that will never exist in production. |
| Declare a `failure_pattern` if your runner can exit zero on failure | A runner that prints its own failure summary and then exits zero produces a false green, and the sandbox builds that runner from the branch under test. |
| Test against the version production runs | Pinned by `database.version`. [Why it matters](/databases/mysql/#restore-into-the-version-production-runs). |
