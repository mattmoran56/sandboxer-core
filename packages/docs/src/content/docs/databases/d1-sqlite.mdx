A D1 or SQLite database is a **file**. That single fact removes almost everything on
[the MySQL page](/databases/mysql/).

| | MySQL | D1 / SQLite |
|---|---|---|
| Install a server | yes | no |
| Start it and wait for it | yes | no |
| Dump the source | yes | no — copy the file |
| Restore into a target | yes | no — copy the file |
| Pin a server version | yes, and it matters | no server, no version |
| Advisory lock for migrations | yes | no |
| Grants and users | yes | no |
| **One writer per database** | no | **yes** |

Seeding is a copy. Forking is a copy. There is no server and no lock.

```yaml
database:
  driver: d1
  seed_from:
    file: .wrangler/state
    fixtures: seeds/fixtures.sql
  migrate:
    command: npx wrangler d1 migrations apply DB --local
  owner: app
```

## One writer per file

This is the one thing you have to get right, and it is the only thing.

**Two processes opening the same D1 file deadlock.** Not "may contend", not "will be slower" —
they hang, or fail with a busy error, and each process looks like it is behaving correctly. The
config must therefore name the single service allowed to own the database:

```yaml
database:
  owner: app
```

<Aside type="danger" title="This is a rule of the engine, not a workaround">
It is tempting to treat this as a bug to be worked around with retries or a longer busy
timeout. It is not. The local runtime that backs D1 holds the file in a way that a second
opener cannot share, and the correct design response is to have exactly one opener. Every
sandbox therefore gets a **private copy** of the file rather than sharing one.
</Aside>

The consequences worth knowing:

- **Two sandboxes never share a database file.** Each has its own, which is the same property
  a MySQL sandbox gets from having its own server — arrived at for free instead of expensively.
- **Every other server is denied the database's location.** Not asked politely to leave it
  alone — the location is simply withheld from any service that is not the owner, so a second
  one fails loudly on a missing binding instead of quietly hanging on a lock. A loud failure is
  much better than a hang.
- **Migration happens before any service starts.** Database provisioning gates the supervised
  processes, so it is the one moment when nothing else holds the file.
- **Fixtures are applied with the SQLite client directly**, not through the project's own
  tooling — for the same reason. The project's tooling would open the file as a second writer.
- **Nothing else may open it.** Not a second service, not a script you run in a shell while
  the app is serving, not a database browser you left open. If a project hangs during
  provisioning, count the openers before you look at anything else.

## Point the runtime at the sandbox's own state directory

This is the one thing a config has to get right, and getting it wrong is quiet.

Both the `migrate` command and the app's `serve` command must direct the runtime at
`$SANDBOXR_D1_DIR`:

```yaml
database:
  driver: d1
  migrate:
    command: npx wrangler d1 migrations apply DB --local --persist-to $SANDBOXR_D1_DIR
  owner: app

frontends:
  apps:
    - label: app
      package: .
      serve: npx wrangler dev --port 8787 --ip 127.0.0.1 --persist-to $SANDBOXR_D1_DIR
      port: 8787
```

Leave it out and the runtime writes its state into `/workspace` — which is **your worktree**.
Three things then go wrong at once:

1. The sandbox's database lands in your branch and shows up in `git status`.
2. Two sandboxes started from the same worktree share one file, so the one-writer rule is
   violated by construction rather than by accident.
3. `sandboxr down` no longer removes the database, because it is not in the sandbox's volume.

None of that errors. It just quietly is not what you asked for.

## The seed is often an empty directory, and that is fine

```yaml
seed_from:
  file: .wrangler/state
```

That path is where the local runtime keeps its SQLite files, and it is normally gitignored. A
**fresh worktree therefore has nothing there.**

That is expected, not an error. The seed artifact is taken from a checkout that does have
state, and with nothing to seed from the driver falls back to migrating an **empty** database.
For a project whose migrations build the schema from nothing, that loses you exactly nothing —
you get a correct, empty database plus fixtures.

If you *want* real content in a new sandbox, the options are the same as anywhere: point
`seed_from.file` at a checkout that has state, or put what you need in
`seed_from.fixtures`.

## Snapshots and diffs

`snapshot()` on a file-based driver is a structure dump — the schema, not the rows — so
[testing a migration](/databases/testing-a-migration/) works identically to MySQL. The
before/after diff answers the same question, and the same rule applies: the baseline is only
re-taken after a **successful** migration, so a failed run's diff still shows what it changed.

The difference is that "throw it away and start again" is a file copy rather than a restore,
so the loop is much faster. On a project like this, `db reset` is close to instant.

## `sqlite` versus `d1`

They are separate drivers because they are seeded differently, not because the engine differs.

| | `sqlite` | `d1` |
|---|---|---|
| Database location | wherever the project puts it | inside the local runtime's state directory |
| Migration command | the project's own | typically the platform CLI's migrations command |
| Binding name | not applicable | the binding the worker declares |

If your project opens a SQLite file directly, use `sqlite`. If it goes through a Workers
binding, use `d1`, because the file layout and the migration command are the platform's rather
than yours.

## Why this driver is the one to start with

If you are evaluating sandboxr and you have a file-database project to try it on, use that one.
No dump to manage, no version to pin, no server to wait for, a sandbox that starts in seconds
and resets instantly. The whole model is easier to see when the database is not the expensive
part.

The complete config is [the Workers example](/config/example-workers-d1/).
