## The short version

A project describes itself in a `sandboxr.yaml` at its repo root: what to build, what
database it needs, which secrets to bring. sandboxr reads that and starts one container per
git worktree, bind-mounting the worktree so your edits are live inside it. A shared router
sends each hostname to the right container.

```bash
cd .worktrees/feat-123
sandboxr up
# https://feat-123.app.acme.sbx.lcl
# https://feat-123.api.acme.sbx.lcl
```

Two sandboxes on two branches do not share a database, a port, an uploads bucket or a
`node_modules` install they can corrupt for each other. Deleting one deletes all of it.

  <Card title="A whole project, not a service" icon="puzzle">
    Every backend the project declares, every front-end, a database seeded from real
    structure, and object storage — inside one container.
  </Card>
  <Card title="Public apps, private controls" icon="approve-check">
    The apps a sandbox serves are shareable by default. Everything that *controls* a
    sandbox sits behind a password, always.
  </Card>
  <Card title="No state to drift" icon="setting">
    Sandbox state lives only in Docker labels. `list` and `gc` are functions of
    `docker ps`, so there is nothing to get out of sync.
  </Card>
  <Card title="Built for agents" icon="rocket">
    The worktree is bind-mounted, so an agent editing inside the container is editing your
    branch. Its work shows up in `git status`.
  </Card>
</CardGrid>
