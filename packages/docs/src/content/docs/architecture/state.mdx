sandboxr keeps **no record of its own sandboxes.** No manifest file, no SQLite database of
what exists, no JSON in `~/.sandboxr` listing running things.

Everything is a container label.

| Label | Meaning |
|---|---|
| `sandboxr.project` | Project name from the config |
| `sandboxr.slug` | The slug |
| `sandboxr.branch` | Branch name, or `?` if it cannot be resolved |
| `sandboxr.commit` | Short commit sha |
| `sandboxr.dirty` | `true` / `false` — uncommitted changes present |
| `sandboxr.worktree` | Absolute path on the host |
| `sandboxr.driver` | Database driver in use |
| `sandboxr.created` | ISO 8601 UTC |
| `sandboxr.access` | `public` / `private` — whether app hostnames need auth |

## What this buys

**`list` and `gc` are pure functions of `docker ps`.** They cannot be stale, cannot be
corrupted, and cannot survive the thing they describe. A container that does not exist cannot
appear in a listing, because the listing *is* the container set.

**The dashboard cannot lie.** It reads labels live, so it cannot disagree with what is actually
running. There is no refresh, no cache invalidation, no "the dashboard says it is up but it is
not".

**Crash recovery is free.** Kill the CLI mid-`up`, reboot the machine, `docker rm` a container
by hand — there is no bookkeeping left inconsistent, because there is no bookkeeping.

**The router needs no configuration file.** It resolves a hostname by matching labels, so
starting a sandbox makes its hostnames work with nothing to write and nothing to reload.

## The alternative, and why it is worse

A manifest file is the obvious design: a JSON file listing sandboxes, updated on `up` and
`down`.

It fails in the ordinary case, not the exotic one. Every one of these leaves it wrong:

- `up` is interrupted after the container starts and before the file is written.
- The machine reboots while a `down` is in progress.
- Somebody runs `docker rm` directly, which people do.
- Two `up` commands run at once and race on the file.
- The file is inside a repository and `git clean` removes it.
- A container is removed by Docker's own pruning.

Each of those is recoverable with a reconciliation step, and the reconciliation step's job is to
compare the file against `docker ps` and believe `docker ps`. At which point the file is a cache
of the thing you are already reading, and its only remaining function is to be wrong
occasionally.

<Aside type="tip" title="The general shape of the argument">
When the truth is already stored somewhere durable that you have to read anyway, a second copy
is not state — it is a bug with a schema.
</Aside>

## The constraints it imposes

This is a real trade, and it is worth being explicit about what you give up.

**A label is a string, so everything must serialise to one.** No nested structures, no lists.
`sandboxr.dirty` is `"true"`, not a boolean.

**Labels are immutable for the life of a container.** You cannot set a label on a running
container; you would have to recreate it. So anything that *changes* while a sandbox runs cannot
be a label:

| Changes at runtime | So it lives |
|---|---|
| Which front-ends have been built | in a file inside the container |
| Whether the last migration succeeded | as a marker inside the container |
| Whether a backend is currently healthy | by asking it, live |
| Current commit, if you commit inside the sandbox | the label records the commit at start |

That last row is a genuine wart: `sandboxr.commit` and `sandboxr.dirty` are a snapshot from
`up`, and they go stale the moment you commit inside the worktree. They are useful for "what was
this started from", not for "what is it now".

<Aside type="caution" title="`degraded` has no label, and that is a gap">
A failed migration marks a sandbox `degraded`, but there is no label for it — a running
container's labels cannot change, so there could not be. It must therefore be derived from
something inside the container, which the contract does not specify. Recorded on
[what is built](/reference/status/).
</Aside>

**Docker's label store is the durability guarantee.** If a container is removed, its state is
gone with it, which is correct for a sandbox — but it also means there is no history. You cannot
ask what sandboxes existed last week.

## What is not in labels

Not everything is ephemeral. Three kinds of thing live in `SANDBOXR_HOME`, and they are all
things that must **outlive** a container:

| Path | Why it is not a label |
|---|---|
| `cache/` | Seed artifacts, shared between sandboxes and expensive to rebuild |
| `logs/<project>/<slug>/` | Survive the container on purpose — the logs from a sandbox you just deleted are the ones you want |
| `tls/`, `state/` | Machine-level, not per-sandbox |
| `secrets/<project>.env` | Per project, and must not be in a container image |
| `build/<project>/<slug>.env` | The generated environment, regenerated on `up` |

`SANDBOXR_HOME` is deliberately **never inside a repository**, so `git clean -xdf` cannot
destroy your seed cache or your certificate.

## Reading the labels yourself

Everything `sandboxr list` shows is available directly, which is occasionally useful:

```bash
docker ps --filter label=sandboxr.project=acme \
  --format '{{.Names}}\t{{.Label "sandboxr.slug"}}\t{{.Label "sandboxr.branch"}}'
```

```
sandboxr-acme-feat-123	feat-123	feat-123
sandboxr-acme-fix-nav	fix-nav	fix/nav-overflow
```

If `sandboxr list` and `docker ps` ever disagree, that is a bug in the listing code, because
there is nothing else it could be.
