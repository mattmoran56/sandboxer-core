Each entry names the obvious approach first, because that is the one you will reach for.

## Two images, not one

**The obvious choice:** one base image with the project's toolchains and dependency tree baked
in. It is simple, and everything is warm.

**Why not:** it can only ever serve one project. The toolchain versions, the database engine and
the dependency tree are all facts about *one repository*, so a second project means a second
multi-gigabyte base.

**Instead:** a small generic base — the supervisor, the router, the object store, `jq`, and the
container scripts — plus a thin per-project layer rendered from a template, holding exactly what
that project's `toolchain:` and `database:` blocks declare. Adding a project costs one layer
rather than another few gigabytes.

**A consequence worth stating:** the project layer's build context holds **only manifests, never
source**. A source change must never be able to re-run a dependency install.

## The container reads a resolved plan, not the config file

**The obvious choice:** mount `sandboxr.yaml` and let the container read it.

**Why not:** then the container has to know how to merge defaults, validate combinations and
compute addresses — in shell, with no schema and no type checker. And it would have to agree
with the host's implementation of the same rules for ever.

**Instead:** the host emits a flattened, fully-resolved `plan.json` and the container reads only
that. Nothing in the container names a service, a port, a package or a route.
[In full](/architecture/plan-json/).

## Debian, not a vendor database image

**The obvious choice:** base the image on the official image for the database the project needs,
and layer a language toolchain on top.

**Why not:** the vendor image is built on a distribution whose glibc is too old for other things
a sandbox has to run. Cloudflare's `workerd` — which anything running `wrangler dev` needs —
requires a newer glibc than that image provides, and fails with `GLIBC_2.35 not found`. No amount
of configuration helps.

**Instead:** Debian bookworm, whose glibc satisfies `workerd`, image-processing libraries, and
every other native module. The cost is installing the database engine separately, which is a
per-project concern anyway.

## MySQL from the vendor's generic tarball, not a package repository

**The obvious choice:** install from the distribution's archive, or from the vendor's own
repository.

**Why not:** the distribution's archive carries a *different* database that is not a drop-in
substitute for a project depending on MySQL collation names or MySQL advisory-lock semantics.
And the vendor's own repository has an **expired signing key**, so the package manager refuses
it outright — there is nothing a Dockerfile can do about that.

**Instead:** the vendor's generic tarball. It pins an exact version rather than tracking whatever
a repository currently serves.

**The cost:** the download host publishes no machine-readable release list, so a version series
resolves through a small pinned table. Go and Node both publish an index and are resolved from
it; this one cannot be.

## The object store is in the base image, not behind a flag

**The obvious choice:** install it only when a project declares `storage:`. It is the largest
thing in the base.

**Why not:** a public sandbox driven by a stranger must not be able to write to production
object storage, and the only reliable way to guarantee that is for the endpoint the code sees to
be **local** — which means the stand-in has to be present whether or not the project remembered
to ask for it.

**Instead:** it is in the base. That is a guarantee, not a feature, so it does not belong behind
a config flag.

## One container per worktree, not one per service

**The obvious choice:** a compose file, one container per service, like production.

**Why not:** the unit you want to throw away is a *branch*, not a service. Per-service
containers mean per-service names, per-service networks, and a database that either is shared —
so two branches with different migrations cannot coexist — or is itself per-branch, at which
point you have re-invented the sandbox with more moving parts. And the whole point is to have
several branches up at once.

**Instead:** one container is one sandbox. `down` removes the container and its volumes and
there is nothing left over. The database lives *inside*, so there is no shared schema for
somebody to find next month and wonder about.

**The cost:** a sandbox is a fat container, and it is not how the project is deployed. It is not
meant to be — it is a development environment, and testing the deployment topology is a
different job.

## State lives only in Docker labels

**The obvious choice:** a manifest file listing sandboxes.

**Why not:** it goes wrong in the ordinary case. Interrupted `up`, reboot mid-`down`, someone
running `docker rm` by hand, two `up`s racing on the file. Each is fixable with a reconciliation
pass whose job is to compare the file with `docker ps` and believe `docker ps` — at which point
the file is a cache of the thing you already have to read.

**Instead:** labels. `list` and `gc` are pure functions of `docker ps`. Nothing can drift,
because there is no second copy.

**The cost:** labels are immutable strings, so anything that changes at runtime cannot be one.
[In full](/architecture/state/).

## Bind-mount the worktree, read-write

**The obvious choice:** copy the source in, or build it into an image.

**Why not:** either adds a sync step to every edit. An image rebuild is minutes, which kills the
loop; a copy needs a watcher, which is a second thing to get wrong and which will get it wrong
during a rebase.

**Instead:** bind mount. Your edit is inside instantly; the container's edit is in your
`git status` instantly. That second direction is what makes
[agents in a sandbox](/agents/in-a-sandbox/) work at all.

**The cost:** anything in the container can rewrite your branch. The container is disposable;
the mount is not.

## Static front-ends are built on demand, never at startup

**The obvious choice:** build everything when the sandbox starts, so it is ready.

**Why not:** a sandbox must come up in seconds, and building six apps takes minutes. Worse, you
almost always want one of them. The other five are pure waiting, every time, for everyone.

**Instead:** nothing is built at startup. An unbuilt hostname answers with a page naming the
command that builds it, and it stays built for the life of the sandbox.

**Why a page and not a 404:** a 404 at a sandbox hostname is indistinguishable from broken DNS
or a misconfigured router, so you would go and debug the wrong layer entirely.

## A static build, not a dev server, for a component library

**The obvious choice:** run the component library's dev server, and get hot reload.

**Why not:** it is a long-lived server holding the whole component library in memory —
commonly several hundred megabytes, permanently, whether or not anyone opens it. The point of
sandboxr is several sandboxes at once under one memory limit, so that cost is paid many times
over for something consulted occasionally.

**Instead:** a static build, on demand, like any other front-end. Tens of seconds when you ask
for it, and nothing at all when you do not.

**The cost:** stories do not hot-reload. Editing a component means rebuilding.

This is the general trade behind [there being no hot reload](/use/edit-and-reload/#there-is-no-hot-reload).

## `all` and `built` are different rebuild sets

**The obvious choice:** one "rebuild the front-ends" command.

**Why not:** the set you want depends on the situation, and the expensive members make one
command wrong. A watcher calling "rebuild everything" on a front-end change would start a
multi-gigabyte site build as a side effect of a component tweak.

**Instead:** `all` is the project's main apps, excluding anything marked `in_build_all: false`.
`built` reads what this sandbox has actually built and refreshes exactly that — so it includes
the expensive apps once you have built them, and never *starts* a first build of one by
accident.

## Three runtime kinds, not two

**The obvious choice:** things with a port, and things that produce files.

**Why not:** a long-running dev server has a port but no build artefact, and no rebuild command
that means anything. Fold it into "backend" and it loses its app hostname; fold it into "static"
and there is nothing to serve. Cloudflare Workers projects need this kind, and so does any
framework without a static export mode.

**Instead:** backend, static, server — declared distinctly, handled distinctly.
[In full](/config/runtime-kinds/).

## A failed migration does not stop the sandbox

**The obvious choice:** fail fast. A container whose database is wrong should not serve.

**Why not:** inspecting a failed migration is one of the main reasons the sandbox exists, and
you cannot get a shell into a container that exited, or diff a schema you cannot reach.

**Instead:** record the failure, mark the sandbox `degraded`, boot everything anyway. Never
silently — the state is in `sandboxr list` and on the dashboard.

## The router is not gated on the database

**The obvious choice:** gate everything on the database being ready, so nothing serves against a
database that is not there.

**Why not:** a first-boot restore legitimately takes minutes, and that is exactly when you most
need to know what is happening. A gated router means the whole sandbox answers "connection
refused" for the whole of its first boot, and a refused connection is not an answer — you cannot
tell a slow restore from a broken one.

**Instead:** the router starts immediately. It serves the status surface and the "not built yet"
pages, neither of which touches the database. A backend that is not up yet answers **502**, and
a 502 is truthful: I am here, that service is not.

The tool sandboxr generalises did gate its router, and its sandboxes were unreachable and
unexplained for the whole of their first boot.

## `static_mode` is explicit, with no clever default

**The obvious choice:** work out how to serve a built directory by looking at what is in it.

**Why not:** the three cases are genuinely different and the wrong guess does not crash. A
single-page app needs every unknown path to fall back to `index.html`; a generator emitting
`about.html` needs `/about` to resolve to it; a plain directory needs an unknown path to be a
**real 404** rather than silently rendering the home page.

Pick one mode for all three and two of them **half-work** — which is much worse than failing,
because you find out from a user rather than from a build.

**Instead:** `static_mode` is `spa`, `files` or `html`, declared per app, defaulting to `spa`.

## The status document is derived, never asserted

**The obvious choice:** have whatever finishes last write `state: "ok"`.

**Why not:** two writers can then disagree, and the one that wrote last wins regardless of which
one was right. A sandbox that reports `ok` while its migration failed is worse than one that
reports nothing.

**Instead:** every writer records a *fact* in its own marker file, and a composer derives the
state from the facts. There is no state field for anyone to set wrongly.

Same principle as [state living only in Docker labels](/architecture/state/), one level down.

## A memory requirement is refused up front

**The obvious choice:** let the build run and report what happens.

**Why not:** what happens is a bare `Killed` and a package manager's exit code 137, neither of
which mentions memory. It reads as a broken build, and people debug their own code.

**Instead:** compare the app's declared `memory` against the container's actual limit and refuse
in **one second**, naming the limit and the fix.

**And a belt as well as braces:** the build also gets a single-process heap ceiling at about 75%
of the limit, so one overrunning process gives up with a heap error rather than being killed
silently. That bounds one process, not their sum — which is exactly why the up-front check has
to exist as well.

## A service that cannot start is omitted, not supervised

**The obvious choice:** declare every service and let supervision deal with the ones that fail.

**Why not:** a service that needs a database no migration creates and that exists on no
developer machine can only crash-loop. It fills the log, it shows red on the dashboard, and it
makes a working sandbox look broken. No amount of supervision improves on that.

**Instead:** leave it out of the plan, or mark it `optional`. And leave a comment where the entry
would go, saying why — otherwise somebody adds it back next quarter.

## The schema baseline is only re-taken after a success

**The obvious choice:** snapshot the schema before each migration attempt.

**Why not:** DDL is not transactional in every engine, so a failed migration leaves a
half-migrated schema. Re-snapshotting on every attempt overwrites the last-known-clean baseline
with that half-migrated state, and the next diff reports **no change** — at exactly the moment
the question matters most, and in a form that reads as reassurance.

**Instead:** baseline after a success, or after a clean restore. Never after a failure.

## Slugs are hashed past 31 characters, not truncated

**The obvious choice:** truncate a long name to fit.

**Why not:** the slug ends up inside a database advisory lock name, which has a length budget.
Two long branch names very often share a prefix — `feature/checkout-part-one` and
`feature/checkout-part-two` — so truncation lets two sandboxes collide on one lock, and one
migration silently waits on the other.

**Instead:** keep the first 22 characters, append `-` and eight characters of the SHA-256 of the
*raw* input. Readable, and collision-free where truncation is not.

## Migration bookkeeping repair was deliberately *not* ported

**The obvious choice:** when a fork inherits a migrations table with rows left unfinished by an
earlier attempt, heal them so the project's runner will proceed.

**Why not:** doing that means reading and writing the project's own bookkeeping schema, which is
reimplementing the project's migration logic — the one thing the driver contract forbids
outright. It also only works for the one project whose schema you encoded.

**Instead:** sandboxr does not touch it. The reasoning is still worth having, and it belongs in
the *project's own runner*:

- **Heal a row by completing it, never by deleting it.** Deleting makes the runner treat a
  half-applied file as pending again, and re-running a migration that already applied half its
  DDL is exactly the hazard the refusal exists to prevent.
- **Never heal a row whose file is still present.** That marks a broken migration as done, and
  the next run fails one migration further along — until the database looks fully migrated
  having never actually run any of it.

**The cost:** a fork of a database in that state will hit the runner's refusal, and you have to
resolve it in the project. That is the correct place for it to surface.

## A migration runner's exit code is not always trusted

**The obvious choice:** the migration command's exit status is the answer.

**Why not:** a runner that prints its own failure summary and then exits zero reports success
while the schema is half-applied. And a sandbox builds that runner **from the branch it is
testing** — so the branch may be exactly the one with that bug.

**Instead:** a project whose runner behaves this way declares a `failure_pattern`, and the
output is checked against it as well as the exit code.

**The related trap:** `cmd | tee log` exits with `tee`'s status, and `tee` always succeeds.
Testing the pipeline reports every failed migration as a success, so the first element of the
pipeline's status is what gets read.

## Migrations run from a directory where no config file resolves

**The obvious choice:** run the migration command from the project root, like a developer would.

**Why not:** a runner that resolves its configuration from relative paths, and loads it without
overriding what is already set, will silently backfill a *partially* set environment from
whichever file it finds. If a production configuration file exists anywhere in the tree, it can
supply the missing half.

**Instead:** run from a directory where none of those relative paths resolve, so the runner
reports that it is configured purely from the environment — per-run proof that nothing shadowed
what the sandbox passed. And refuse outright if a production-pointing variable is set in the
caller's environment.

## Restore into the declared database version, not the developer's

**The obvious choice:** use whatever the source database is running. It is the same data.

**Why not:** a laptop's `latest` tag drifts, and often lands on a release line production will
never run. A migration is only meaningfully tested against the version it will really run on.

**Instead:** `database.version` names the version, the fork is restored into it, and any skew
from the source is reported on every dump.

## The dashboard runs the real CLI

**The obvious choice:** implement start, stop and rebuild in the web server. It is a few
functions.

**Why not:** it is not a few functions. Volume names keyed on a lockfile hash, seed cache
invalidation, plan resolution, the worktree checkout cases — a second
implementation drifts from the first within a week, and then the dashboard and the CLI disagree
about what a sandbox is.

**Instead:** the dashboard shells out to the same code path. One consequence worth naming: the
dashboard is only as reliable as the code it reads, so while a source file is half-saved every
button fails in whatever way that file fails. A dashboard should recognise its own toolchain's
diagnostics and say "the CLI is mid-edit or broken" rather than reporting a mystery.

## Actions are a closed table

**The obvious choice:** one endpoint that runs a command, with the command in the request.

**Why not:** the dashboard talks to the Docker socket. A generic command endpoint behind a
password is a remote shell with an extra step, and a session-stealing bug becomes total
compromise instead of a bounded one.

**Instead:** a fixed table in the server. Each entry names the command, whether progress can be
a real fraction, and how to parse a line into progress. Nothing outside the table can run.

## Actions stream over two transports, not one

**The obvious choice:** WebSockets for everything. One mechanism.

**Why not:** most actions are one-way — a build, a migration, output flowing out. Server-Sent
Events is the simpler tool for that: plain HTTP, reconnects on its own, works through anything
that speaks HTTP.

**Instead:** SSE for one-way output, WebSocket for the terminal, which is genuinely
bidirectional. Four event kinds — `start`, `log`, `step`, `done`.

**The related decision:** the progress bar is a real fraction only where the output carries one,
and an honest indeterminate bar where it does not. An invented percentage is worse than no
percentage, because people plan around it.

## The terminal is a route inside the dashboard

**The obvious choice:** give the terminal its own hostname, like everything else.

**Why not:** app hostnames are `public` by default. A terminal on a per-sandbox hostname is one
config mistake away from being an interactive shell, on the internet, in a container that mounts
your worktree.

**Instead:** `/p/<project>/s/<slug>/terminal`, inside the dashboard, on the bare domain. It
inherits the dashboard's session and there is no second auth path to get wrong.

## Public sandboxes are refused, not warned

**The obvious choice:** print a warning and let the developer decide.

**Why not:** neither failure is recoverable. Leaked records cannot be un-leaked; spend cannot be
un-spent. And warnings appear during `up`, a command you run dozens of times a day while
thinking about something else — they scroll, they become familiar, and familiar warnings are
invisible.

**Instead:** refuse to start. `access.apps: private` is the escape hatch, and it is one line in a
diff that a reviewer sees. [In full](/security/public-sandboxes/).

## The router's domain comes from the environment, in one place

**The obvious choice:** write the domain into the router config. It rarely changes.

**Why not:** it ends up written in it many times, and then a domain override *silently does
nothing*. Every request lands on the catch-all and nothing says why.

**Instead:** the router config is generated at every boot from the plan and the environment, and
the domain is read once. Host matchers are exact — `<slug>.<label>.<project>.<domain>` — and an
unknown host answers 404 **naming the host it was asked for**, so a mismatch identifies itself.

## Per-service log files, trimmed rather than rotated

**The obvious choice:** let everything write to stdout and read `docker logs`.

**Why not:** `docker logs` interleaves every process in the container and cannot be filtered
after the fact. On a sandbox running three APIs, a database and a dev server that is unreadable —
for a person, and for an agent trying to find its own failure.

**Instead:** one file per service. And they are *trimmed*, not rotated: these are development
logs, and a sandbox left up for days must not be able to fill its own disk.

## `SANDBOXR_HOME` is never inside a repository

**The obvious choice:** keep state next to the project, in `.sandboxr/`.

**Why not:** `git clean -xdf` is a normal thing to run, and it would destroy the seed cache, the
certificate and every sandbox's logs.

**Instead:** `~/.sandboxr` by default, outside every repo.

<Aside type="tip" title="The pattern in all of these">
Each of these is the same shape: the obvious design fails in the *ordinary* case rather than an
exotic one, and the failure's symptom does not resemble its cause. That is what makes them worth
writing down — anyone re-deriving the design from first principles will reach the obvious answer
first, and the reason it was rejected is not visible from the code.
</Aside>
