`sandboxr.yaml` is the human-facing file. **Nothing inside a container ever reads it.**

The host resolves it into a flattened, fully-resolved projection at `/sandboxr/plan.json`,
mounted read-only, and that file is the container's entire view of the project. Nothing in the
container's scripts names a service, a port, a package or a route — all of it comes from the
plan.

## Why the boundary is here

**One image serves every project.** A multi-service monorepo on MySQL and a single-worker
project on a file database run from the same generic container. That is only possible if the
container knows nothing about either — the plan is what makes it generic.

**Resolution belongs where the type checker is.** Merging defaults into every entry, validating
that a `serve:` app has a `port`, computing a URL from a slug and a domain — all of that is
easy in TypeScript and miserable in shell. The container side has `jq` and nothing more.

**A flat plan has nothing left to infer.** Every default already merged, every optional field
either present or absent. A script reading the plan never has to reproduce a defaulting rule,
which is the classic way two implementations of one config drift apart.

## What the plan contains

```jsonc
{
  "project": "acme",

  "database": {
    "driver": "mysql",                  // mysql | d1 | sqlite | none
    "version": "8.4",
    "name": "acme",                     // defaults to the project name
    "owner": "app",                     // file drivers: the one service that may open it
    "fixtures": "db/seeds/fixtures.sql",
    "seed": { "path": "acme-3f2a1b.sql.zst", "anonymised": true },
    "migrate": {
      "workdir": "services",            // omitted means run in an empty directory
      "command": "go run ./cmd/migrate",
      "since": "20240101",              // exported as SANDBOXR_MIGRATE_SINCE
      "failure_pattern": "[0-9]+ failed",
      "file_pattern": "[0-9]{8}-[^ ]+\\.sql",
      "error_pattern": "Error [0-9]+ \\([0-9A-Z]+\\):.*"
    }
  },

  "storage": { "driver": "minio", "buckets": ["uploads", "avatars", "exports"] },
  "toolchain": { "go": "1.23", "node": "22" },

  "deps": {                             // omitted entirely if there is no Node tree
    "root": "web",
    "lockfile": "package-lock.json",
    "install": "npm ci --no-audit --no-fund"
  },

  "services": [
    { "kind": "backend", "name": "api", "label": "api", "port": 8001,
      "health": "/health", "workdir": "services",
      "build": "go build -o {out} ./{name}", "optional": false },

    { "kind": "static", "label": "app", "package": "web", "root": "web/packages",
      "build": "npx vite build", "out": "dist",
      "static_mode": "spa", "in_build_all": true },

    { "kind": "server", "label": "cms", "package": "cms", "root": "web/packages",
      "serve": "npx next dev --port 3000 --hostname 127.0.0.1", "port": 3000,
      "prepare": "npm run codegen", "optional": true }
  ],

  "routes": { "app": { "/api": "api", "/cms": "cms" } },
  "env": { "DB_HOST": "${SANDBOXR_DB_HOST}", "S3_BUCKET": "uploads" }
}
```

Note the single `services` array. `backends` and `frontends` are a *human* distinction — they
read better in a config file — but at runtime all three
[runtime kinds](/config/runtime-kinds/) are the same sort of thing with a `kind` field.

## `env` is the join between two vocabularies

```jsonc
"env": { "DB_HOST": "${SANDBOXR_DB_HOST}", "APP_URL": "${SANDBOXR_URL_APP}" }
```

The container computes **where** things are. The project reads **its own names** for them.
Something has to join the two, and only the project knows its own spelling — so the plan
carries the mapping.

Values are expanded with `envsubst`, which substitutes `${...}` and **does not run a shell**.
A value in the plan is therefore data and can never be a command. That is deliberate: the plan
is generated from a file in a project repository, and a project repository is not a trust
boundary you want handing shell strings to your container's init.

## What the container computes for itself

The contract forbids importing anything that describes *where* something runs — importing a
developer's `DB_HOST` would point the sandbox at their own database. So the entrypoint derives
these and exports them under a `SANDBOXR_` prefix:

| Variable | When |
|---|---|
| `SANDBOXR_DB_DRIVER`, `SANDBOXR_DB_NAME`, `SANDBOXR_DB_DIR` | always |
| `SANDBOXR_DB_HOST`, `_PORT`, `_USER`, `_PASSWORD` | `mysql` |
| `SANDBOXR_DB_FILE` | `sqlite` |
| `SANDBOXR_D1_DIR`, `SANDBOXR_D1_OWNER` | `d1` |
| `SANDBOXR_S3_ENDPOINT`, `_KEY`, `_SECRET`, `_REGION` | storage declared |
| `SANDBOXR_URL_<LABEL>` | one per app label |
| `SANDBOXR_PORT_<SERVICE>` | one per port-holding service |
| `SANDBOXR_MIGRATE_SINCE` | when `migrate.since` is set |

`SANDBOXR_URL_<LABEL>` exists because only the container knows both the slug and the domain at
the moment a build runs. Same-origin API calls do not need it — the router serves `/api` on the
app's own hostname — but **cross-app navigation does**, because a link from one app to another
needs an absolute, slug-bearing URL.

<Aside type="tip" title="`migrate.since` is passed as an environment variable, not a flag">
The tool cannot guess a runner's flag spelling. So `since` arrives as
`SANDBOXR_MIGRATE_SINCE` and the command in the config has to consume it if it wants it:

```yaml
migrate:
  command: go run ./cmd/migrate --since "$SANDBOXR_MIGRATE_SINCE"
```
</Aside>

## File-backed drivers must be pointed at the sandbox's state directory

This is the one thing a project config has to get right for `d1` and `sqlite`, and getting it
wrong is quiet rather than loud.

Both the `serve` and `migrate` commands must direct the runtime at `$SANDBOXR_D1_DIR`:

```yaml
database:
  migrate:
    command: npx wrangler d1 migrations apply DB --local --persist-to $SANDBOXR_D1_DIR
  owner: app

frontends:
  apps:
    - label: app
      package: .
      serve: npx wrangler dev --port 8787 --ip 127.0.0.1 --persist-to $SANDBOXR_D1_DIR
      port: 8787
```

Without it the runtime writes its state **into the worktree** instead of the sandbox. Which
means: the sandbox's data lands in your branch, two sandboxes on the same worktree share one
database file, and the [one-writer rule](/databases/d1-sqlite/#one-writer-per-file) is violated
by construction.

## What the container mounts

| Path | What |
|---|---|
| `/workspace` | the worktree, bind-mounted read-write |
| `/sandboxr/plan.json` | the plan, read-only |
| `/sandboxr/cache` | the seed artifact cache, read-only |
| `/var/log/sandboxr` | per-sandbox logs, so they survive the container |
| `/var/lib/sandboxr/data` | the `data` volume — the database |
| `/var/lib/sandboxr/blob` | the `blob` volume — object storage |
| `/var/lib/sandboxr/bin` | the `bin` volume — built binaries |
| `/srv/www` | the `www` volume — built sites |
| `/workspace/<deps.root>/node_modules` | the shared `deps-<hash>` volume |

Plus `SANDBOXR_SLUG`, which is required. `SANDBOXR_DOMAIN`, `SANDBOXR_PROJECT`,
`SANDBOXR_WITH` and the storage and database credentials all have defaults.

## Two images, not one

The image is split, and the split is what lets one machine serve several projects cheaply.

```
sandboxr/base:<version>            generic, one per machine, ~400 MB
    └── sandboxr/<project>:<hash>  toolchains + database engine + dependencies
            └── one container per worktree
```

- **The base** is Debian, the process supervisor, the router, the object store, `jq`, and the
  container scripts. Nothing project-specific. It stays small so that adding a project costs
  one thin layer rather than another few gigabytes.
- **The project layer** is rendered per project from a template, adding exactly what that
  project's `toolchain:` and `database:` blocks declare, plus its dependency install.

The build context for the project layer holds **only manifests, never source**, so a source
change can never re-run a dependency install. The worktree arrives at run time, as a bind
mount.

<Aside type="note" title="Why this is a structural improvement over the predecessor">
The tool sandboxr generalises baked one project's toolchains *and* its whole dependency tree
into a single very large base image. It worked, and it could never have served a second
project — the toolchain versions, the database engine and the dependency tree were all facts
about one repository.
</Aside>
