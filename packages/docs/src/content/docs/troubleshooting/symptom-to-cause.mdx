Ordered by how misleading the symptom is, not by how common it is. The entries near the top are
the ones that waste hours.

<Aside type="caution" title="Where these came from">
Every entry is a failure that actually happened while building the tool sandboxr generalises.
The causes transfer even where command names do not. See
[what is built](/reference/status/).
</Aside>

## The five worst

### MySQL will not start, and reports a corrupt database

**What you see**

```
InnoDB: Operating system error number 28
InnoDB: Error number 28 means 'No space left on device'
InnoDB: ... probably out of disk space
[ERROR] [MY-012574] [InnoDB] Unable to open data file
```

or, part-way through a restore, a message about a corrupt tablespace.

**What it actually is: the Docker disk is full.**

InnoDB running out of space mid-write reports it as a data-file problem, and the phrasing reads
as a *corrupt database* rather than a full one. People spend an afternoon on recovery
procedures for a disk problem.

**Check disk before you believe anything else a failing database tells you.**

```bash
docker system df
sandboxr gc            # prunes the build cache, which grows fastest of anything here
```

The shared base image is around 4.5 GB and each sandbox adds a few hundred MB of volumes, but
**Docker's build cache** is the thing that actually fills the disk, and nothing except `gc`
cleans it up.

### A build died with `code 137`

**What you see**

```
   Collecting page data ...
Killed
npm ERR! Lifecycle script `build` failed with error:
npm ERR! code 137
```

Nothing about memory. Nothing about limits. It reads like a broken build.

**What it actually is: the kernel's OOM killer.** `137` is `128 + 9` — killed by `SIGKILL`.

A static site generator rendering a few thousand pages spreads work across many worker
processes, so no single `--max-old-space-size` bounds it. The **cgroup total** is what the kernel
measures.

```yaml
frontends:
  apps:
    - { label: www, package: marketing, build: npm run build, out: out, memory: 6g }
```

or for one run:

```bash
sandboxr up --memory 8g
```

<Aside type="danger" title="And it may not be your build that dies">
On a machine with several sandboxes running, a heavy build gets *something* OOM-killed, and that
something can be another sandbox — or your own local database container. Stop what you are not
using before a big build.
</Aside>

A build script should refuse up front when the limit is below what it needs, printing the limit
and the fix. One second with a named cause beats twenty with `code 137`.

### A restart changed nothing

**What you see:** you edit code, restart the service, and the old behaviour persists. Or every
restart logs `address already in use` while the service carries on serving quite happily.

**What it actually is: the supervised process is a shell, not your service.**

A run script that pipes its output —

```bash
exec my-service | tee /var/log/my-service.log     # wrong
```

— makes the **shell** the supervised process. A restart signals the shell. Your service is a
child, survives, keeps holding its port, and every replacement dies on the port while the old
code answers requests.

```bash
exec my-service >> /var/log/my-service.log 2>&1   # right
```

Redirect with `>>`. Never pipe. The symptom is "my change did nothing", and you will read your
own code for a long time before you read a run script.

### Login succeeds and then every API call returns 401

**What you see:** the login flow completes, the app loads, and every single request to the API
comes back 401. Nothing points at configuration.

**What it actually is: two identity settings were merged that must not be.**

An identity provider can serve the same tenant on both a custom domain and a provider-issued
domain. Fold a browser-side domain variable into the server-side one because they "look like the
same thing", and one service rejects the other's token as having an **invalid issuer**.

Keep them separate:

```yaml
secrets:
  rename:
    VITE_AUTH0_DOMAIN: SANDBOXR_AUTH0_SPA_DOMAIN
    VITE_AUTH0_CLIENT_ID: SANDBOXR_AUTH0_SPA_CLIENT_ID
```

[The full explanation](/config/secrets/#two-names-must-not-be-merged).

### Two sandboxes' migrations hang, one at a time

**What you see:** a migration in one sandbox sits there. Another sandbox migrated fine ten
minutes ago. There is no error.

**What it actually is: two slugs collided on one advisory lock.**

If a slug is *truncated* to fit a lock-name budget rather than hashed, two long branch names
that share a prefix produce the same lock name. `feature/checkout-part-one` and
`feature/checkout-part-two` truncate identically, so one migration waits on the other's lock
with nothing to indicate why.

The slug ceiling is 31 characters, and anything over it keeps 22 characters plus eight
characters of a hash of the raw input. [Why](/databases/mysql/#the-advisory-lock-and-why-slugs-are-hashed).

### A migration "succeeded" and the schema is half-applied

**What you see:** the migration output ends with something like `3 applied, 1 failed`, the exit
code is 0, and the sandbox reports itself healthy.

**What it actually is: the runner exits zero after printing its own failure summary.**

And the sandbox builds that runner **from the branch under test**, so the branch may be exactly
the one with that bug. Declare a pattern so the output is checked as well as the exit code:

```yaml
migrate:
  command: go run ./cmd/migrate
  failure_pattern: "[0-9]+ failed"
```

<Aside type="caution" title="The related trap, if you are writing this code">
`cmd | tee log` exits with `tee`'s status, and `tee` always succeeds. Testing the pipeline's
status reports **every** failed migration as a success. Read the first element of the pipeline's
status array instead.
</Aside>

## DNS, certificates and routing

### Nothing resolves

```
curl: (6) Could not resolve host: feat-123.app.acme.sbx.lcl
```

**Locally:** the resolver is not installed, or `sandboxr init` could not elevate.

```bash
cat /etc/resolver/sbx.lcl          # should exist
dscacheutil -q host -a name feat-123.app.acme.sbx.lcl
sandboxr doctor
```

`ping` is the wrong test on macOS — it does not use the `/etc/resolver` mechanism, so a name
that works in the browser can still fail to ping.

**On a server:** the wildcard record is missing, or it is one level too shallow. `*.sbx.example.com`
does **not** match `feat-123.app.acme.sbx.example.com`; DNS wildcards match exactly one label.
You need `*.acme.sbx.example.com`.

### The browser warns about the certificate

Locally: the development CA is not in the trust store, or the certificate predates the domain
you are now using. Re-run `sandboxr init`.

On a server: you are serving the local development CA's certificate. It only works because your
own machine was told to trust it. You need real certificates via ACME with a **DNS-01**
challenge — HTTP-01 cannot issue a wildcard.

### Reading the response you got

Once DNS and TLS work, the status code tells you exactly which layer to look at.

| Response | Means |
|---|---|
| Nothing answers at all | The shared router found no container. `sandboxr list`, then `sandboxr up`. |
| **404 naming the host it was asked for** | You reached a sandbox and its internal router does not serve that hostname. A wrong label, or a domain mismatch. |
| **502** | The label is right and the backend behind it is not up yet. Truthful during a first boot. |
| **503 with build instructions** | The app simply is not built. `sandboxr reload --app <label>`. |
| A 404 from something that is clearly an API | A `routes` prefix pointing at the wrong service, or misordered prefixes. |

Fastest single check:

```bash
curl https://feat-123.app.acme.sbx.lcl/__sandboxr/live       # `ok` means both hops work
curl https://feat-123.app.acme.sbx.lcl/__sandboxr/status.json # booting / ok / degraded
```

Those answer on **every** hostname a sandbox serves, and the router is deliberately not gated on
the database — so they answer during a first boot too, which is exactly when you need them.

### A domain override appears to do nothing

Every request lands on a catch-all 404 and nothing explains why.

The internal router's config is generated at every boot and reads the domain from
`SANDBOXR_DOMAIN` in one place. If you have edited a *static* router config somewhere, or
hardcoded the domain, the override cannot take effect — the predecessor tool had its domain
written into thirteen places and its override silently did nothing.

Check what the sandbox thinks its domain is:

```bash
curl https://<hostname>/__sandboxr/status.json     # includes "domain"
```

### An API request 404s, and the route definitely exists

You reached the wrong service. `routes` maps a path prefix on one app's hostname to one service,
and two apps commonly use the same prefix for different services:

```yaml
routes:
  app:
    "/api": api
  admin:
    "/api": adminApi      # not `api` — the admin app's paths are /admin/*
```

Also check ordering: prefixes match most-specific-first, so `"/api/admin"` must be declared
before `"/api"` or `/api` swallows it.

## Front-end builds

### Every app says "not built yet", even ones you just built

If you are writing the internal router config: a file matcher resolves against the **document
root**. Testing for `index.html` before setting the root always misses, so every built app
reports itself as unbuilt.

Set the root first, then test.

### The build fails with `code 127` naming a binary that is definitely installed

`127` is command-not-found.

An image that installs dependencies from manifests alone will skip linking a workspace `bin`
whose target file does not exist at install time. The script that calls it then fails with a
bare `127`, naming a binary that is plainly in the dependency tree.

The dependency-seeding step must re-link workspace bins after seeding.
[Context](/architecture/startup/#dependency-caching-and-why-deps-init-exists).

### An app "works" but deep links are wrong

Three variants, all `static_mode`:

| What happens | Cause | Fix |
|---|---|---|
| Every route except `/` is a 404 | A single-page app being served as `files` | `static_mode: spa` |
| A deep link renders the home page instead of the page | A static-site generator being served as `spa` | `static_mode: html` |
| A typo'd asset filename returns HTML with a 200 | An asset directory being served as `spa` | `static_mode: files` |

None of these is a crash, which is why the mode is declared rather than inferred. You find out
from a user otherwise. [The three modes](/config/runtime-kinds/#static_mode-three-ways-to-serve-a-directory).

### A dependency change did not take effect

`reload` does not touch dependencies. The shared `node_modules` volume is keyed on the lockfile
hash, so a lockfile change needs:

```bash
sandboxr up
```

## Databases

### `Error 1044: Access denied ... to database 'acme_...'`

The grant is missing, or its underscore is not escaped. MySQL treats `_` as a wildcard in the
database part of a `GRANT`:

```sql
GRANT ALL ON `acme\_%`.* TO 'sandbox'@'%';
```

`acme_%` unescaped grants far too widely. `` `acme_%` `` in plain backticks grants on a database
*literally named* `acme_%`, and every fork then fails with 1044.

### `Refusing to run until these are resolved`

A previous migration failed and left incomplete bookkeeping. **The runner is protecting you** —
this is correct behaviour, not a bug.

```bash
sandboxr db diff       # what landed
sandboxr db reset      # start clean
```

A fork heals this in the *copy* by setting the completion timestamp, never by deleting the row —
deleting would make the runner re-run a migration that already applied half its DDL.
[Why](/databases/mysql/#stuck-migration-bookkeeping-is-healed-not-deleted).

### The pending migration count differs from another worktree

**Expected.** The set is computed from *that worktree's* migration directory, which is exactly
the "what would this branch do" question you wanted answered.

### A restore succeeded but binary columns are garbage

The dump is missing `--hex-blob`. Binary columns are otherwise emitted as escaped string
literals and any charset mismatch in the pipe corrupts them — silently, because the restore
succeeds.

### A permissions error on a statement nobody wrote

The dump is missing `--set-gtid-purged=OFF`, so it carries a `SET @@GLOBAL.GTID_PURGED` that
needs elevated privileges and poisons the target's GTID state if it does apply.

### A D1 or SQLite migration hangs

Two processes are opening the same file. Two writers deadlock on a busy lock, which turns a slow
boot into a hang **with nothing in the log**, and neither process looks like it is misbehaving.

Exactly one service may own a file-based database, named by `database.owner`. Count the openers
— including a shell, a script, or a database browser you left open — before looking at anything
else. [Why](/databases/d1-sqlite/#one-writer-per-file).

### A sandbox's database file appears in `git status`

The runtime is not being pointed at the sandbox's own state directory, so it is writing into
`/workspace` — your worktree.

Both the migrate command and the app's serve command need `--persist-to $SANDBOXR_D1_DIR`:

```yaml
migrate:
  command: npx wrangler d1 migrations apply DB --local --persist-to $SANDBOXR_D1_DIR
```

Two sandboxes from one worktree will also be sharing that file, so this is usually the real cause
of a hang as well. [Details](/databases/d1-sqlite/#point-the-runtime-at-the-sandboxs-own-state-directory).

### `migrate.since` seems to be ignored

It is exported as `SANDBOXR_MIGRATE_SINCE` rather than added to the command as a flag — sandboxr
cannot guess a runner's flag spelling. **Your command has to reference it:**

```yaml
migrate:
  command: go run ./cmd/migrate --since "$SANDBOXR_MIGRATE_SINCE"
  since: "20240101"
```

## The sandbox itself

### `sandboxr list` shows `degraded`

The container is up and the migration failed. **This is intended** — the services boot so you
can inspect the failure.

```bash
sandboxr logs feat-123 db-init
sandboxr db diff
sandboxr shell
```

### Every dashboard button fails with a strange error

The dashboard runs the real CLI, so while a source file is half-saved every button fails in
whatever way that file fails. Check the CLI is syntactically valid before debugging the
dashboard.

### The dashboard cannot list pull requests

Pull-request data needs an authenticated API call, which runs host-side with `gh`. Without `gh`
authenticated the dashboard still works and links to a branch search instead.

### A worktree was created but git exited non-zero

A repository hook can run *after* the checkout is already on disk, and fail. A `post-checkout`
hook depending on a tool the machine does not have does exactly this.

**The tree on disk decides whether it worked, not the exit code.** Check whether the directory
exists and has content before treating it as a failure.

### git refuses to create a worktree for a branch

git will not check out one branch in two places, and the branch behind a pull request is very
often already open in your main checkout. That needs a detached worktree at the branch's ref
rather than a normal one — three situations, three different commands:

| Where the branch is | What is needed |
|---|---|
| A local branch nothing has checked out | `git worktree add <path> <branch>` |
| A local branch checked out somewhere else | `git worktree add --detach <path> refs/heads/<branch>` |
| Only on the remote | `git worktree add -b <branch> <path> origin/<branch>` |

Guessing wrong produces a git error that says nothing about what to do next, which is why
`sandboxr ensure` decides rather than leaving it to git's inference.

### A sandbox exists for a worktree that is gone

```bash
sandboxr gc --dry-run
sandboxr gc
```

`gc` reads the `sandboxr.worktree` label and reaps sandboxes whose path no longer exists. Such a
sandbox is unreachable anyway — you cannot rebuild anything in it.

## Still stuck?

Work down the layers in this order. Each one is cheap and rules out the one below it.

1. `sandboxr doctor` — Docker, DNS, certificate, router, password, disk.
2. `docker system df` — disk, because a full disk lies about what it is.
3. `sandboxr list` — is the sandbox running, and is it `degraded`?
4. `sandboxr logs <slug>` — everything, interleaved.
5. `sandboxr logs <slug> db-init` — seeding, migration, fixtures.
6. `sandboxr shell` — look for yourself.
