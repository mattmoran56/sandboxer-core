A sandbox needs some real credentials — an identity provider, an analytics key — and must
never receive others. The `secrets` block draws that line explicitly, per project.

```yaml
secrets:
  read:
    - services/api/.env
    - services/adminApi/.env
    - web/packages/web/.env
  keep:
    - AUTH0_DOMAIN
    - AUTH0_AUDIENCE
    - AUTH0_CLIENT_ID
    - AUTH0_CLIENT_SECRET
    - ANALYTICS_API_KEY
    - EMAIL_API_KEY
    - JWT_SECRET
  rename:
    ANALYTICS_API_HOST: ANALYTICS_ENDPOINT
    VITE_AUTH0_DOMAIN: SANDBOXR_AUTH0_SPA_DOMAIN
  never:
    - "DB_*"
    - "MYSQL_*"
    - "S3_*"
    - "*_URL"
    - "PORT"
    - "ENV"
```

| Field | What it does |
|---|---|
| `read` | Files to read variables from, relative to the repo root. Usually the `.env` files developers already have. |
| `keep` | An allowlist of names to import. Anything not listed is dropped. |
| `rename` | Import a variable under a different name. |
| `never` | A denylist of glob patterns, applied after everything else. |

Imported values are written to `~/.sandboxr/secrets/<project>.env`, mode 0600, and the
generated per-sandbox environment goes to `~/.sandboxr/build/<project>/<slug>.env`.

## Names only, never values

The import prints a **count and a list of names**. It never prints, logs or echoes a value.

```
$ sandboxr secrets import
read 3 files
imported 11 names:
  AUTH0_AUDIENCE  AUTH0_CLIENT_ID  AUTH0_CLIENT_SECRET  AUTH0_DOMAIN
  ANALYTICS_API_KEY  EMAIL_API_KEY  JWT_SECRET  MAPS_API_KEY
  SANDBOXR_AUTH0_SPA_CLIENT_ID  SANDBOXR_AUTH0_SPA_DOMAIN  SANDBOXR_AUTH0_SPA_AUDIENCE
dropped 24 names not in `keep`
refused 6 names matching `never`: DB_HOST DB_USER DB_PASSWORD S3_ENDPOINT API_URL PORT
```

That is a deliberate design goal rather than politeness: it means the command is safe to run
with someone watching, in a screen share, or in a terminal whose scrollback ends up in a bug
report.

## Anything describing *where* something runs is never imported

This is the rule that prevents the worst failure mode in the whole system.

`DB_*`, `MYSQL_*`, `S3_*`, `*_URL`, `PORT` — these describe **location**, not identity. A
sandbox computes all of them itself: its database is inside its own container, its object
storage is inside its own container, its services reach each other on internal ports.

Import them and you get a sandbox pointed at **the developer's own database** or at **real
cloud storage**. Nothing errors. The app works. Test uploads land in a production bucket, and
a migration you were testing safely runs against something that was not a copy.

<Aside type="danger" title="This is why `never` is a denylist applied last">
`keep` is an allowlist, so in principle nothing unlisted gets through. `never` is a second,
independent barrier applied after it, because the cost of one mistake in `keep` is a
production write. Two mechanisms for one rule is the right amount here.
</Aside>

Put the patterns in `never` even when they are not in `keep`. It documents the intent, and it
protects the next person who adds a variable to `keep` without thinking about it.

## Why `rename` exists

It looks like a convenience. It is not; it is load-bearing in two distinct situations.

### The same value has two names

A codebase drifts. The `.env` files say `ANALYTICS_API_HOST`; the code reads
`ANALYTICS_ENDPOINT`. Nobody is going to renormalise every `.env` file on every developer's
machine, so the config aliases one to the other:

```yaml
rename:
  ANALYTICS_API_HOST: ANALYTICS_ENDPOINT
```

### Two names must **not** be merged

This is the important one, and it is the case people get wrong.

A browser-side identity setting and a server-side one can legitimately differ. An identity
provider can serve the same tenant on both a custom domain and a provider-issued domain. If
you fold `VITE_AUTH0_DOMAIN` into `AUTH0_DOMAIN` because they "look like the same thing", one
service will reject the other's token as having an **invalid issuer**.

The symptom is memorable and misleading: **login succeeds**, the user lands in the app, and
then every single API call comes back 401. Nothing in that picture points at a variable name.

So the browser-side values are kept under their own names:

```yaml
rename:
  VITE_AUTH0_DOMAIN: SANDBOXR_AUTH0_SPA_DOMAIN
  VITE_AUTH0_CLIENT_ID: SANDBOXR_AUTH0_SPA_CLIENT_ID
  VITE_AUTH0_AUDIENCE: SANDBOXR_AUTH0_SPA_AUDIENCE
```

They are then injected into the front-end build under whatever names that build expects,
without ever colliding with the server-side pair.

## Public sandboxes: dummies unless opted in

If `access.apps` is `public`, third-party credentials must be **dummies** unless explicitly
opted in. Anyone who can drive a public app can otherwise make it send real email, spend real
LLM credit, or write to a real analytics property.

This is enforced as a refusal to start, not a warning. It, and the seed requirement that goes
with it, are on [public sandboxes](/security/public-sandboxes/).

<Aside type="caution" title="The opt-in mechanism is not specified yet">
The contract says "unless explicitly opted in" but defines no field for the opt-in, and
neither example has one. Until the schema lands, expect a public project to need either
dummy values in `keep` or `access.apps: private`. Recorded on
[what is built](/reference/status/).
</Aside>

## What a sandbox provides for itself

You never put these in `secrets`, and they should be in `never`:

| Category | Examples | Why |
|---|---|---|
| Database location and credentials | `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `MYSQL_*` | The database is inside the sandbox. |
| Object storage | `S3_ENDPOINT`, `S3_ACCESS_KEY`, bucket names | Storage is inside the sandbox. |
| Inter-service URLs | `API_URL`, `*_URL` | Computed from the config's ports and labels. |
| Ports | `PORT` | Comes from `backends.services[].port`. |
| Environment name | `ENV`, `NODE_ENV` | The sandbox decides. |
| CORS allowlists | `CORS_ALLOWED_ORIGINS` | Derived from the sandbox's own hostnames. |

That last row is worth noting: because the sandbox computes its own CORS allowlist from its
own hostnames, a new sandbox needs no API-side configuration at all. The only external system
that needs telling about a sandbox hostname is your **identity provider**, and one wildcard
per app label covers every slug for ever. [How](/start/prerequisites/).
