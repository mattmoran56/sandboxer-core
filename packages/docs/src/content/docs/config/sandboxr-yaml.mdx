`sandboxr.yaml` lives at the **root of the project being sandboxed** — not in the sandboxr
repo. It is versioned with that project's code, which is the point: a new service and the
config that knows how to run it land in the same commit, so a branch that adds a service gets
a sandbox that runs it with no coordination.

The authoritative schema is `packages/core/src/config/schema.ts`. This page is the human
description; where they disagree, the schema wins.

<Aside type="note" title="Where the shape in these docs comes from">
`contracts.md` §5 sketches this file, but its snippet is not valid YAML — it shows a
`defaults:` mapping key as a sibling of block-sequence items. The example configs in
`examples/` use `backends: { defaults, services }` and `frontends: { root, defaults, apps }`,
and that is the shape documented here. Recorded as a bug on
[what is built](/reference/status/).
</Aside>

## Identity

```yaml
project: acme
sandboxr: ">=0.1.0"
```

| Field | Required | What it does |
|---|---|---|
| `project` | yes | The project's name. Must match `[a-z0-9-]`. Appears in every hostname, container name and volume name, so changing it orphans every running sandbox. |
| `sandboxr` | recommended | The minimum tool version this config needs. A mismatch is a clear error at parse time rather than a confusing failure later. |

Set `sandboxr` the moment you use a field that a previous version did not have. It costs
nothing and it turns "why is the CMS not starting" into one sentence.

## `database`

```yaml
database:
  driver: mysql
  version: "8.4"
  seed_from:
    local:
      container: acme_db
      database: acme
    file: /var/sandboxr/seeds/acme.sql.zst
    fixtures: db/seeds/fixtures.sql
  migrate:
    workdir: services
    command: go run ./cmd/migrate --dir ../db/migrations --non-interactive
    since: "20240101"
```

| Field | What it does |
|---|---|
| `driver` | `mysql`, `d1`, `sqlite` or `none`. Picks the whole implementation. [The driver model](/databases/drivers/). |
| `version` | Driver-specific. For MySQL, the server version to restore *into*. |
| `seed_from.local` | Fork a database container running on the same machine. Read only, always. |
| `seed_from.file` | Restore a dump instead. Required on a server, where there is no local container. |
| `seed_from.fixtures` | A SQL file applied **after** migrations. |
| `migrate.command` | The project's own migration command. sandboxr never reimplements it. |
| `migrate.workdir` | Directory to run that command from, relative to the repo root. |
| `migrate.since` | A cutoff passed to the project's runner, for projects that adopted migration tracking part-way through their life. |

Four of these deserve their reasons spelled out.

**`version` is the version production runs, not the one you happen to have.** A laptop's
`mysql:latest` tag drifts, and it commonly resolves to a release line that production will
never run — sometimes one that is already end-of-life. A migration is only meaningfully
tested against the version it will really run on, so the fork is restored into the declared
version and any skew from the source is reported.

**`fixtures` runs after migrations, and a failure is not fatal.** Fixtures encode schema
assumptions; a fixture that no longer matches is a *useful signal* that the branch changed
something, not a reason to refuse to start a sandbox. It is reported and the sandbox comes
up.

**`migrate.command` is shelled out to, never reimplemented.** sandboxr may read migration
state to display progress, but the thing that actually runs is the project's own program.
Reimplementing it would mean two migration engines that must agree for ever, and they would
not.

**`since` exists because an empty cutoff selects every file on disk.** In a project that
adopted a migrations tracking table part-way through its life, the files that predate the
table were applied before it existed — so re-running them fails on columns that already
exist. Pin the cutoff the project's own runner defaults to. The pending set is
per-worktree, which is why two branches legitimately report different counts.

<Aside type="caution" title="`since` arrives as an environment variable, not a flag">
sandboxr cannot guess a runner's flag spelling, so `since` is exported as
`SANDBOXR_MIGRATE_SINCE` and **your command has to consume it**:

```yaml
migrate:
  command: go run ./cmd/migrate --since "$SANDBOXR_MIGRATE_SINCE"
  since: "20240101"
```

Setting `since` without referencing it in the command does nothing at all.
</Aside>

**A file-backed driver must be pointed at the sandbox's own state directory.** For `d1` and
`sqlite`, both the `migrate` command and the app's `serve` command need it:

```yaml
migrate:
  command: npx wrangler d1 migrations apply DB --local --persist-to $SANDBOXR_D1_DIR
```

Without it the runtime writes into the worktree rather than the sandbox — so sandbox data lands
in your branch, and two sandboxes from one worktree share a file they must not share.

<Aside type="caution" title="Precedence between `local` and `file` is unspecified">
Both can be set, and nothing in the contract says which wins, or whether the choice is made
by environment. The example's comments imply "`local` on a laptop, `file` on a server". Until
the schema lands, set only the one you mean on a given machine.
</Aside>

Other `database` fields the examples use:

| Field | Driver | What it does |
|---|---|---|
| `owner` | `d1`, `sqlite` | Names the single service allowed to open the database file. **Required** for these drivers — two writers deadlock. [Why](/databases/d1-sqlite/#one-writer-per-file). |

## `backends`

Long-running processes that listen on a port, built once to a binary and supervised.

```yaml
backends:
  defaults:
    workdir: services
    build: go build -o {out} ./{name}
    health: /health
  services:
    - { name: api, port: 8001, label: api }
    - { name: adminApi, port: 8081, label: admin-api }
    - { name: jobs, port: 8004, label: jobs }
```

| Field | Where | What it does |
|---|---|---|
| `name` | per service | The service's directory name and its identity in `logs`, `reload` and `routes`. |
| `port` | per service | The port it listens on **inside** the container. Nothing is published to the host, so these only have to be unique within the sandbox. |
| `label` | per service | The hostname component. `api` becomes `feat-123.api.acme.sbx.lcl`. Omit it and the service has no hostname of its own — reachable only through a `routes` prefix. |
| `build` | defaults or per service | How to produce the binary. `{name}` and `{out}` are substituted. |
| `workdir` | defaults or per service | Where to run the build, relative to the repo root. |
| `health` | defaults or per service | A path that returns 200 when the service is ready. Used to decide whether to report the backend as up. |

Anything in `defaults` can be overridden on one service. A service with no `build` and no
default cannot be built, and that is an error at parse time rather than at boot.

<Aside type="tip" title="Leave out a service that cannot possibly work">
If a service needs a database that exists on no developer machine and that no migration
creates, declaring it only produces a crash-loop and a red tile. Leave it out, and put a
comment in the config saying why — otherwise someone adds it back in six months.
</Aside>

## `frontends`

Either built to a directory, or run as a long-running server. Both live here; the difference
is `out:` versus `serve:`. See [three runtime kinds](/config/runtime-kinds/).

```yaml
frontends:
  root: web/packages
  defaults:
    build: npx vite build
    out: dist
  apps:
    - { label: app, package: web }
    - { label: admin, package: admin }
    - { label: www, package: marketing, build: npm run build, out: out, memory: 6g }
    - { label: storybook, package: storybook, build: npm run build-storybook, out: storybook-static, in_build_all: false }
    - { label: cms, package: cms, serve: npx next dev --port 3000 --hostname 127.0.0.1, port: 3000, optional: true }
```

| Field | What it does |
|---|---|
| `root` | Prefix for every `package` path, so a monorepo does not repeat itself. |
| `label` | The hostname component, and the name `reload --app` takes. |
| `package` | Directory, relative to `root`. `.` means the repo root — a single-app project. |
| `build` | The build command. Runs in the package directory. |
| `out` | Where the build lands, relative to the package. Its presence makes this a **static** app. |
| `static_mode` | `spa` (default), `html` or `files` — how the built directory is served. |
| `serve` | A long-running command instead of a build. Its presence makes this a **server** app. |
| `prepare` | A one-off command run before a `serve:` process starts — codegen, a schema sync. |
| `port` | Required with `serve`. The port the server listens on inside the container. |
| `memory` | Per-app memory ceiling for the build. Raise it for anything rendering thousands of pages. |
| `optional` | `true` means it does not start unless you pass `--with <label>`. |
| `in_build_all` | `false` excludes it from `reload --app all`. Default `true`. |

Three of these are load-bearing:

**`static_mode` is explicit because the wrong value half-works.** A single-page app needs every
unknown path to fall back to `index.html`; a generator emitting `about.html` needs `/about` to
resolve to it; an asset directory needs an unknown path to be a real 404. One mode cannot cover
all three, and the failure is an app that works in some places rather than a build that fails.
[The three modes](/config/runtime-kinds/#static_mode-three-ways-to-serve-a-directory).

**`build` should usually be the bundler, not the npm script.** A typical `npm run build` is
`tsc -b && vite build`, so a branch that does not typecheck cannot be sandboxed at all.
Calling the bundler directly means a branch mid-refactor still gets a running app, and CI
remains the thing that enforces types. That is a deliberate division: the sandbox is for
*looking at behaviour*, CI is for correctness.

**`in_build_all: false` protects the fast path.** `reload --app all` is what a file watcher
calls on any front-end change. If a multi-gigabyte site build is in `all`, editing one shared
component starts one. [The distinction in full](/use/edit-and-reload/#all-and-built-are-not-the-same-thing-on-purpose).

## `routes`

Path prefixes per app hostname, mapping to a backend or a server front-end.

```yaml
routes:
  app:
    "/api": api
    "/cms": cms
  admin:
    "/api": adminApi
  www:
    "/api": api
```

The key is an app `label`; each entry maps a path prefix on that hostname to a service name.
So `https://feat-123.app.acme.sbx.lcl/api/users` reaches the `api` backend, and everything
else on that hostname is served by the app's static files.

**Why bother, when every backend already has its own hostname?** Because same-origin paths
keep the bundle free of cross-origin requests and take CORS out of the picture entirely. No
preflights, no allowlist to maintain per sandbox, no cookie `SameSite` surprises. It also
means the app's own code needs no sandbox-specific configuration: `/api` is `/api` in every
environment.

Order matters where prefixes overlap. `"/api/admin"` must come before `"/api"`, and the more
specific prefix wins.

Note the `admin` entry above pointing at `adminApi` rather than `api`. That is the common
real case: two apps use the same path prefix for two different services. Getting it wrong
produces a 404 from a service that never had those routes, which looks like a bug in the app.

## `secrets`

Covered in full on [its own page](/config/secrets/), because the rules matter more than the
fields.

```yaml
secrets:
  read: [services/api/.env]
  keep: [AUTH0_DOMAIN, JWT_SECRET]
  rename: { ANALYTICS_API_HOST: ANALYTICS_ENDPOINT }
  never: ["DB_*", "S3_*", "*_URL"]
```

## `storage`

Object storage inside the sandbox, so uploads never reach a real bucket.

```yaml
storage:
  driver: minio          # minio | none — default none
  buckets: [uploads, avatars, exports]
```

`buckets` are created at first boot. The sandbox computes its own endpoint and credentials and
injects them, which is why `S3_*` belongs in `secrets.never` — importing the developer's real
storage config would send a sandbox's test uploads to a production bucket.

The object store is present in the shared base image whether or not a project declares
`storage:`, so that a public sandbox driven by a stranger *cannot* reach real cloud storage. That
is a guarantee rather than a feature, which is why it is not behind a flag — but a project that
declares no buckets pays no runtime cost, because the service is not started.

## `toolchain`

```yaml
toolchain:
  go: "1.23"
  node: "22"
```

The versions installed in the **per-project image layer**, not in the shared base. The base
image is generic — the supervisor, the router, the object store, `jq` and the container
scripts — and knows nothing about Go or Node. A toolchain is a fact about one repository, so
it belongs in that repository's own layer.

Changing one rebuilds the project layer (`sandboxr image build`), not the base. That is a
minutes-scale rebuild rather than a tens-of-minutes one, and it affects only sandboxes of this
project — but it does affect all of them, so treat a toolchain bump as its own change rather
than a drive-by.

The prefix you give is resolved against the vendor's release index, so `node: "24"` picks the
latest 24.x at build time. [Whether a prefix picks the release a project
meant](/reference/status/) has not been verified against a real build.

## `access`

```yaml
access:
  apps: public       # public | private
  controls: password # password is the only option today
```

| Value | Meaning |
|---|---|
| `apps: public` | App hostnames need no authentication. Brings [two hard requirements](/security/public-sandboxes/) with it, enforced as refusals. |
| `apps: private` | App hostnames are behind the same session as the dashboard. The escape hatch when you need real data. |
| `controls: password` | Not optional and not configurable away. |

## Adding a service, end to end

<Steps>

1. **Declare it.** One line under `backends.services`, inheriting the defaults:

   ```yaml
   backends:
     services:
       - { name: api, port: 8001, label: api }
       - { name: adminApi, port: 8081, label: admin-api }
       - { name: jobs, port: 8004, label: jobs }
       - { name: search, port: 8005, label: search }   # new
   ```

   Pick a port nothing else in the sandbox uses. Give it a `label` only if it should answer
   on a hostname of its own; a service that only ever serves one app's `/api` prefix does not
   need one.

2. **Route to it, if an app calls it.**

   ```yaml
   routes:
     app:
       "/api/search": search
       "/api": api
   ```

   More specific prefix first, or `/api` swallows it.

3. **Give it any secrets it needs.** Add its `.env` to `secrets.read` and its variable names
   to `secrets.keep`. Nothing describing *where* things run — it will be told that.

4. **Bring the sandbox up again.** `sandboxr up` reconciles the running container with the
   new config.

   ```bash
   sandboxr up
   sandboxr logs feat-123 search -f
   ```

5. **Check it.** `https://feat-123.search.acme.sbx.lcl/health` if you gave it a label, or
   `https://feat-123.app.acme.sbx.lcl/api/search/...` through the route.

6. **Commit the config with the service.** The two belong in one commit. A reviewer who
   checks out the branch gets a sandbox that runs it, with nothing to configure.

</Steps>
