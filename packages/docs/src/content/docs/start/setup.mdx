This is once per machine, not once per project. It installs three things: a way for
`*.sbx.lcl` to resolve, a certificate the browser trusts, and the shared router that maps a
hostname to a container.

```bash
sandboxr init      # DNS, certificate, and the shared router
sandboxr doctor    # check it, and say what is missing
```

<Aside type="caution" title="Not verified">
`sandboxr init` and `sandboxr doctor` follow the tool sandboxr is ported from. Neither
exists in `packages/cli` yet, so the commands on this page have not been run. The
*requirements* — a wildcard resolver, a trusted certificate, one shared router — are
structural and will not change. See [what is built](/reference/status/).
</Aside>

## Laptop or server: pick one

The difference is entirely DNS and certificates. Everything after this page is identical.

| | Laptop | Remote server |
|---|---|---|
| Domain | `sbx.lcl`, resolved locally only | A real domain with a wildcard record |
| DNS | A local resolver, one `sudo` line | Wildcard `A`/`AAAA` at your DNS provider |
| Certificate | A locally-trusted CA that only your machine trusts | ACME, from a real certificate authority |
| Reachable by | You | Anyone who can resolve the name |

<TabItem label="Laptop">

## 1. DNS for a wildcard suffix

Every sandbox hostname is a different name under one suffix, and there can be dozens. You do
not want to edit `/etc/hosts` for each one, so `init` installs a resolver that answers for
the whole suffix at once.

On macOS that is one line in `/etc/resolver/sbx.lcl`, which is why `init` needs `sudo`
exactly once. If it cannot elevate it prints the command for you to run:

```bash
sudo mkdir -p /etc/resolver
echo "nameserver 127.0.0.1" | sudo tee /etc/resolver/sbx.lcl
```

`sbx.lcl` is deliberately not a real top-level domain, so nothing you do here can shadow a
name you actually need.

Check it:

```bash
dscacheutil -q host -a name feat-123.app.acme.sbx.lcl
```

<Aside type="tip" title="`ping` is the wrong test on macOS">
macOS's `ping` does not use the `/etc/resolver` mechanism, so a name that resolves correctly
in the browser can still fail to ping. Use `dscacheutil` or just open the URL.
</Aside>

## 2. A certificate your browser trusts

The apps are served over HTTPS, because a browser treats an origin without it differently in
ways that will waste your afternoon: secure cookies are dropped, service workers do not
register, and some identity providers refuse a plain-HTTP redirect URI outright.

`init` creates a local certificate authority, adds it to the system trust store, and issues
one wildcard certificate covering the whole suffix. Both land in `SANDBOXR_HOME`:

<FileTree>
- ~/.sandboxr
  - tls/
    - **cert.pem** the wildcard certificate
    - **key.pem** its private key
  - state/ router config, dashboard session secret
  - cache/ database seed artifacts
  - logs/
</FileTree>

Adding a CA to the trust store is a real privilege escalation on your own machine — a
certificate signed by it will be trusted for *any* name. Keep the key where `init` puts it,
mode 0600, and do not copy it to a shared machine. A server should use real certificates
instead; see the other tab.

## 3. The shared router

One router process for the whole machine, on a shared `sandboxr` Docker network. It
terminates TLS with the certificate from step 2, reads the `Host` header, and forwards to the
right container by container name.

There is exactly one, for every project and every sandbox. See
[how a request arrives](/architecture/request-path/).

## 4. The control password

```bash
export SANDBOXR_PASSWORD='a long random string'
```

Put it in your shell profile so it survives a reboot. On a laptop this protects the
dashboard, the terminal and every action endpoint against anything else running on your
machine — which is a smaller threat than a server faces, but the requirement is the same
because the mechanism is the same.

## 5. Check it

```bash
sandboxr doctor
```

`doctor` is meant to be run when something is wrong, and to *name what is missing* rather
than exit non-zero. Expect it to check that Docker is reachable, that the resolver file
exists and answers, that the certificate is present and not expired, that the router is
running on the shared network, that `SANDBOXR_PASSWORD` is set, and that there is enough free
disk to restore a database.

</TabItem>
<TabItem label="Remote server">

A server changes three things: DNS is real, certificates are real, and the machine is
reachable by people who are not you. That last one is why
[access and security](/security/two-tiers/) is not optional reading.

<Steps>

1. **A wildcard DNS record.**

   Sandbox hostnames are four labels deep — `<slug>.<label>.<project>.<domain>` — so a
   single-level wildcard is not enough. `*.sbx.example.com` matches
   `app.sbx.example.com` but **not** `feat-123.app.sbx.example.com`.

   You need either a wildcard per project:

   ```
   *.acme.sbx.example.com.   A   203.0.113.10
   *.worker-thing.sbx.example.com.   A   203.0.113.10
   sbx.example.com.                  A   203.0.113.10
   ```

   or, if your DNS provider supports multi-level wildcards, one record. Most do not. Adding a
   record per project is a small cost and it makes the set of projects on a host explicit.

   The bare `sbx.example.com` record is the **dashboard**, which never lives on a
   per-sandbox hostname.

2. **Real certificates.**

   Use ACME with a **DNS-01** challenge, not HTTP-01. HTTP-01 cannot issue a wildcard, and
   you need wildcards — one per project, plus the bare domain. That means giving the router
   an API credential for your DNS provider, scoped to the one zone.

   ```bash
   export SANDBOXR_ACME_EMAIL='ops@example.com'
   export SANDBOXR_DOMAIN='sbx.example.com'
   # plus your DNS provider's API token, per the provider's own variable name
   ```

   Do not reuse the local CA from the laptop path. It only works because your own machine
   was told to trust it.

3. **The password, properly.**

   ```bash
   export SANDBOXR_PASSWORD="$(openssl rand -base64 32)"
   ```

   Store it in whatever secret manager the machine already uses. It is compared
   timing-safely and stored as a hash, and it is never logged — but a password in a shell
   history file is still a password in a shell history file.

4. **Firewall.** Open 80 and 443. Nothing else. Sandbox containers publish no host ports at
   all, so there is nothing else to open. The Docker socket must not be exposed over TCP,
   ever — the dashboard reaches it over a mounted Unix socket.

5. **Seed from a dump, not a fork.**

   `seed_from.local` forks a database container running on the same machine. On a server
   there is no such container, and pointing one at a production database would be exactly
   the mistake the driver contract exists to prevent. Use `seed_from.file` with an
   anonymised dump, and put it somewhere the host can read:

   ```yaml
   database:
     seed_from:
       file: /var/sandboxr/seeds/acme.sql.zst
   ```

6. **Read [public sandboxes](/security/public-sandboxes/) before you point the DNS record at
   the machine.** Two requirements are enforced as refusals, and understanding *why* takes
   two minutes now instead of an incident later.

</Steps>

The full checklist, including what to verify before opening it up, is
[the deployment guide](/server/deployment/).

## What `init` wrote

Everything lives under `SANDBOXR_HOME`, default `~/.sandboxr`. It is deliberately **never
inside a repository**, so `git clean -xdf` cannot destroy your seed cache or your
certificate.

| Path | What it holds |
|---|---|
| `cache/` | Database seed artifacts, content-addressed |
| `logs/<project>/<slug>/` | Per-sandbox logs — these survive the container |
| `tls/` | Certificate and key |
| `state/` | Router config, dashboard session secret |
| `secrets/<project>.env` | Third-party credentials, mode 0600 |
| `build/<project>/<slug>.env` | The generated per-sandbox environment |
| `bin/` | Host-built helper binaries |
