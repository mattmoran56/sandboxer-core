You have [set up the machine](/start/setup/) and the project has a `sandboxr.yaml` at its
repo root. This page gets one sandbox running.

## Start it

A sandbox comes from a **worktree**, not from a branch you check out in place. Make one, then
bring it up from inside it:

```bash
git worktree add .worktrees/feat-123 feat-123
cd .worktrees/feat-123
sandboxr up
```

The slug defaults to the worktree directory name, so nothing needs naming. `feat-123` looks
like a ticket id, so that is what the slug becomes — and the same id in a *branch* name would
have been found too. The full derivation order is on [the glossary](/reference/glossary/#slug).

If you would rather not think about worktrees:

```bash
sandboxr ensure feat-123
```

That finds a worktree already on the branch and syncs it, or creates one under
`.worktrees/<slug>` and starts it. It never offers your **main checkout**, even when
the branch is checked out there — a sandbox bind-mounts its worktree, and that has no
business pointing at the tree you have open in an editor.

<Aside type="note" title="Why a worktree and not a branch">
Two sandboxes on two branches need two directories on disk, because each is bind-mounted
into its own container. A worktree is git's own answer to "the same repository, checked out
twice", and it costs almost nothing: one directory, sharing the object store.
</Aside>

## What the first thirty seconds do

<Mermaid
  caption="First boot. The slow part is the database; the front-ends are deliberately not built."
  chart={`

  i -->|"yes"| j["Supervise the backends"]

/>

Roughly, on the monorepo in [the worked example](/config/example-mysql-monorepo/):

| Step | Cost |
|---|---|
| Everything except the database | a few seconds |
| Restoring a cached database seed | most of the remaining time |
| **Total, cache warm** | ~30 seconds |
| First ever run, base and project images not built | tens of minutes, once |

<Aside type="caution" title="Measured elsewhere, not here">
These figures were measured on one large monorepo using the internal tool sandboxr
generalises, not against sandboxr itself. Your project's numbers will differ; the *shape* —
database dominates, front-ends cost nothing yet — will not.
</Aside>

## The URLs you get

`up` prints them. Every `backends[]` and `frontends[]` entry with a `label` gets one:

```
https://feat-123.app.acme.sbx.lcl      the main single-page app
https://feat-123.api.acme.sbx.lcl      the API behind it
https://feat-123.admin.acme.sbx.lcl    the admin app
https://feat-123.www.acme.sbx.lcl      the marketing site
https://sbx.lcl                        the dashboard (every sandbox, every project)
```

Read a hostname as `<slug>.<label>.<project>.<domain>`.

The **dashboard** is the odd one out: it is on the bare domain, it covers every sandbox and
every project, and it is behind the password. The terminal is a *route inside it* —
`/p/acme/s/feat-123/terminal` — rather than a hostname of its own, so it inherits the
dashboard's session and cannot accidentally be exposed on a public app hostname.

## "Not built yet"

Open the app URL immediately after `up` and you will very likely get a page saying the app
has not been built, and naming the command that builds it.

That is not a failure. **Static front-ends are built on demand, never at startup.** A
sandbox must come up in seconds; building every app first would make that impossible, and
most of the time you only care about one of them.

```bash
sandboxr reload --app app
```

Then refresh. From then on that app stays built for the life of the sandbox, and
`reload --app built` refreshes exactly the ones this sandbox has actually built.

<Aside type="tip" title="The page tells you the command">
The not-built page names the app and the command. That is the entire reason it exists rather
than a 404 — a 404 at a sandbox hostname is indistinguishable from DNS being broken, and you
would go and debug the wrong thing.
</Aside>

## Check it is healthy

```bash
sandboxr list
```

```
SLUG        PROJECT   BRANCH              STATE      APPS BUILT   AGE
feat-123    acme      feat-123            running    app          4m
fix-nav     acme      fix/nav-overflow    degraded   –            2h
```

`degraded` <Badge text="important" variant="caution" /> means the sandbox started but its
migration failed. That is deliberate: a failed migration does **not** stop a sandbox, because
inspecting a failed migration is one of the main reasons the sandbox exists. The services
boot, you can get a shell, and you can diff the schema.

```bash
sandboxr db diff       # what the failed run actually changed
sandboxr logs feat-123 db-init
```

## If it did not come up

<Steps>

1. **Nothing resolves.** DNS, not sandboxr. `sandboxr doctor` first, then
   [troubleshooting](/troubleshooting/symptom-to-cause/#nothing-resolves).

2. **The browser warns about the certificate.** The local CA is not trusted, or the
   certificate predates the domain you are now using. Re-run `sandboxr init`.

3. **MySQL will not start.** Check free disk *first*. A full Docker disk reports itself as a
   corrupt database, and you will otherwise spend an hour on the wrong problem.
   [Details](/troubleshooting/symptom-to-cause/#mysql-will-not-start).

4. **A build died with `code 137`.** That is the kernel's OOM killer, reported by npm with no
   mention of memory. Raise the limit.
   [Details](/use/edit-and-reload/#memory-limits).

5. **Login bounces on a callback mismatch.** The sandbox hostname is not on your identity
   provider's allowlist. One wildcard per app label fixes it for ever;
   [prerequisites](/start/prerequisites/) has the list of fields.

</Steps>

## Throw it away

```bash
sandboxr down feat-123
```

Container, database and object storage, all gone. Because the database lives *inside* the
container there is no shared schema left behind to find later.

The **worktree on disk is left alone**, so deleting a sandbox never loses work. Commits you
made inside it are still commits.
