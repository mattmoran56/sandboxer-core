sandboxr runs host-side in Node and does its work through Docker. It needs no other daemon,
no Kubernetes, and no cloud account.

## Required

| Thing | Minimum | Why |
|---|---|---|
| **Docker** | Any version with `docker compose` and BuildKit | Everything runs in containers, and the base image is built with BuildKit. |
| **Node.js** | 22 or newer | `package.json` sets `"engines": { "node": ">=22" }`. |
| **Git** | 2.30 or newer | `git worktree` with `--detach` and porcelain output are both used. |
| **A POSIX shell** | – | The scripts *inside* the container are bash. Nothing host-side is. |

Optional but worth having:

| Thing | What it buys you |
|---|---|
| **`gh`, authenticated** | The dashboard can list open pull requests and start a sandbox from one. Without it the dashboard still works and links to a branch search instead. |
| **A local database container** | On a laptop, `seed_from.local` forks the database you already run, so a sandbox starts from real structure with no dump file to manage. |

<Aside type="note" title="Why `gh` runs on the host, not in the container">
Resolving a pull-request number needs an authenticated API call, and fetching a pull
request's branch needs credentials from your keychain. A token has no business inside a
container whose only job is rendering a page, and no container can read the keychain
anyway. Both happen host-side, and the dashboard degrades gracefully without them.
</Aside>

## Sizing

<Tabs>
  <TabItem label="Laptop">

Measured on the monorepo in [the worked example](/config/example-mysql-monorepo/), with
every service running:

| | Cost |
|---|---|
| One sandbox | ~560 MB memory |
| The shared router | ~40 MB |
| The DNS resolver | ~15 MB |
| The shared base image | ~4.5 GB disk, once |
| Each sandbox's volumes | a few hundred MB |

On an **8 GB Docker VM** that is five or six sandboxes, comfortably. Below 8 GB you will
spend your time being OOM-killed.

Disk is the tighter constraint in practice, and Docker's *build cache* grows fastest of
anything here. `sandboxr gc` prunes it; nothing else does.

  </TabItem>
  <TabItem label="Remote server">

Take the laptop numbers and add headroom for concurrency, because a server is shared:

- **Memory:** 1 GB per sandbox you intend to hold, plus 2 GB for the host and the shared
  router, plus whatever a heavy front-end build peaks at. Eight concurrent sandboxes wants
  16 GB, not 8.
- **Disk:** 40 GB is a sane floor. The base image is ~4.5 GB, each sandbox's volumes are a
  few hundred MB, and the build cache will happily take everything else.
- **CPU:** builds are the only bursty part. Four cores is enough for a small team; two will
  feel slow when two people rebuild at once.

Full detail, including what to check before you open it to the internet, is in
[the deployment guide](/server/deployment/).

  </TabItem>
</Tabs>

<Aside type="caution" title="A full Docker disk does not report itself as a full disk">
When disk runs out mid-restore, InnoDB reports "probably out of disk space" part-way
through, which reads as a *corrupt database*. If a sandbox's MySQL will not start, check
free space before you believe anything else it says. This one has cost real hours — see
[troubleshooting](/troubleshooting/symptom-to-cause/#mysql-will-not-start).
</Aside>

## Memory limits are per sandbox, and 2 GB is not always enough

The default per-sandbox limit is 2 GB. That is fine for APIs and single-page apps, and not
fine for a static site generator rendering thousands of pages:

- `next build` spreads work across many worker processes, so no single
  `--max-old-space-size` bounds it. The **cgroup total** is what the kernel kills.
- The failure surfaces as npm's `code 137` and a bare `Killed`, with no mention of memory.

Raise it per app in the config (`memory: 6g` on the app's entry) or for the whole sandbox
with `SANDBOXR_MEMORY_LIMIT`. See
[the edit–reload loop](/use/edit-and-reload/#memory-limits).

## What you also need, and it is not software

<Steps>

1. **A domain.** Locally, a fake one is fine and `sbx.lcl` is the default. On a server it
   must be a real domain you control, because you need a **wildcard** DNS record and a real
   certificate.

2. **`sudo`, once.** Local DNS needs one line written into a system resolver file.
   `sandboxr init` prints the command if it cannot elevate.

3. **Your identity provider's allowlists updated.** If the project's apps log in through
   Auth0, Okta, Cognito or anything else that validates redirect URLs, every sandbox
   hostname must be allowed or login dead-ends on a callback mismatch. One **wildcard per
   app label** covers every slug for ever:

   ```
   https://*.app.acme.sbx.lcl
   https://*.admin.acme.sbx.lcl
   ```

   Add each to the allowed callback URLs, logout URLs, web origins and CORS origins. If your
   tenant refuses a wildcard — web origins is the field most likely to — you will need to
   maintain the lists per sandbox against a **development-only** application, never the one
   production uses.

4. **A password for the controls.** `SANDBOXR_PASSWORD`. There is no default and there is no
   way to turn the requirement off. [Why](/security/two-tiers/).

</Steps>
