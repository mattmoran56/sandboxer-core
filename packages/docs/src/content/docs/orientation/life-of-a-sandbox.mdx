This page follows one sandbox from beginning to end. It is the same ground as
[the map](/orientation/map/), told as a story rather than as a layout, and it is the fastest way
to build a mental model of the whole thing.

The example throughout is a fictional project called **acme**: three APIs, a few front-end apps,
and a MySQL database. The branch is `feat-123`.

## Before anything: a worktree

A sandbox is made from a **worktree** — git's own way of having the same repository checked out
in two directories at once. Two branches running at the same time need two directories, because
each one is mounted into its own container.

```bash
git worktree add .worktrees/feat-123 feat-123
cd .worktrees/feat-123
```

Nothing has happened yet. This is just a directory.

## Step 1 — you run the command

```bash
sandboxr up
```

## Step 2 — sandboxr works out what it is looking at

It searches upwards from the current directory for a `sandboxr.yaml`, reads it, and checks every
field. A misspelled setting is an error that names the setting, not a value that silently does
nothing.

Then it works out the sandbox's short name — its **slug**. You did not give one, so it looks at
the directory name `feat-123`, spots something shaped like a ticket id, and uses that.

<Detail summary="the full slug derivation, the character rules and the length ceiling">

In order of preference:

1. an explicit argument (`sandboxr up my-name`)
2. a ticket-style id anywhere in the worktree directory name, matched by `/[a-z]+-[0-9]+/i`
3. that same pattern in the branch name
4. the branch name
5. the worktree directory name

Then sanitised: lower-cased, every character outside `[a-z0-9-]` becomes `-`, runs of `-`
collapse, leading and trailing `-` are stripped.

**Ceiling is 31 characters.** Over that, keep the first 22 characters, append `-`, and append the
first 8 characters of the SHA-256 of the *raw* input.

Hashed rather than truncated because the slug ends up inside a MySQL advisory lock name, and
MySQL's `GET_LOCK` truncates at 64 characters. Two long branch names very often share a prefix —
`feature/checkout-part-one` and `feature/checkout-part-two` — so truncation would let two
sandboxes collide on one lock and one migration would silently wait on the other.

Implementation: `packages/core/src/naming.ts`. Contract: §3.1.

</Detail>

## Step 3 — the safety check

If the project's apps are set to be **public** — reachable by anyone who knows the URL — sandboxr
checks two things before it does anything else, and **refuses to start** if either fails:

- The database must not be seeded by copying a live database, and a dump file counts only if
  somebody has explicitly marked it as anonymised.
- Real third-party credentials must not be present, unless the settings opt in to that.

These are refusals rather than warnings because neither failure can be undone. Leaked records
stay leaked; money spent on somebody else's API calls stays spent.
[The full reasoning](/security/public-sandboxes/).

## Step 4 — the database seed is prepared, on your computer

Before the container exists, sandboxr produces a **seed artifact**: a reusable copy of the
database to start from. On a laptop that usually means copying from a database container you
already run. On a server it means reading a dump file.

The artifact is cached in `~/.sandboxr/cache/`, so the second sandbox of the same project does
not repeat the work.

<Aside type="note" title="The source database is only ever read">
Every destructive step in sandboxr targets a copy. That single property is what makes it safe to
point a half-written migration at real structure and real volume.
</Aside>

<Detail summary="why the seed is produced on the host rather than baked into the image">

If the seed lived in the image, the image would need rebuilding every time the source database
changed — which for a project under active development is daily. Producing it on the host and
mounting the cache read-only means the image only changes when the *toolchain* changes.

The cache is content-addressed, so an unchanged source produces the same artifact name and no
work. Driver code: `packages/core/src/drivers/`.

</Detail>

## Step 5 — the plan is written

sandboxr now turns the project's settings into the file the container will read. Every default is
merged in, every hostname is computed, and the three kinds of thing a project can run are
flattened into one list.

It also writes an environment file for this one sandbox. It is deliberately tiny: the slug, the
project, the domain, and the credentials the sandbox's own database will be created with.
Everything else the container works out for itself.

<Detail summary="why the host tells the container almost nothing">

Contract §5.2 forbids importing anything that describes *where* something runs. Importing a
developer's `DB_HOST` would point a disposable copy at their real database; importing storage
credentials would point it at real cloud storage.

So the container derives those and exports them under a `SANDBOXR_` prefix, and the project's
settings map those names onto the project's own names. The host supplies only the handful of
facts the container cannot work out: which worktree this is, which domain it answers on, and the
credentials for the services it is about to create.

Files: `packages/core/src/sandbox/env.ts`, `packages/core/src/config/plan.ts`.

</Detail>

## Step 6 — the container starts

One `docker run`. The important parts of it:

- The worktree is **bind-mounted** at `/workspace`, read and write. Your edits are inside
  instantly. The container's edits are in your `git status` instantly.
- The plan is mounted read-only.
- Four private volumes are attached: the database, the object storage, the built binaries, and
  the built websites.
- A shared volume holds the installed dependencies, keyed on the lockfile, so every sandbox with
  the same dependencies shares one install.
- Labels record the project, slug, branch, commit, worktree path and access setting.
- **No host ports are published at all.** A shared router reaches the container by name.

<Detail summary="every mount and label, and the memory rule">

Mounts:

| Inside the container | What it is |
|---|---|
| `/workspace` | the worktree, read-write |
| `/sandboxr/plan.json` | the plan, read-only |
| `/sandboxr/cache` | the host seed cache, read-only |
| `/var/log/sandboxr` | per-sandbox logs, so they outlive the container |
| `/var/lib/sandboxr/data` | the database volume |
| `/var/lib/sandboxr/blob` | the object-storage volume |
| `/var/lib/sandboxr/bin` | built binaries |
| `/srv/www` | built websites |
| `/workspace/<deps root>/node_modules` | the shared dependency volume |

Labels (contract §3.4): `sandboxr.project`, `sandboxr.slug`, `sandboxr.branch`,
`sandboxr.commit`, `sandboxr.dirty`, `sandboxr.worktree`, `sandboxr.driver`, `sandboxr.created`,
`sandboxr.access`.

Memory: the whole sandbox gets one limit, and it is the largest limit any single app in the
project asks for, with a floor of 4 GB. The cgroup total is what the kernel enforces, so one
app's `memory: 6g` has to raise the container's limit, not just its own.

Code: `packages/core/src/sandbox/run.ts`.

</Detail>

## Step 7 — the inside comes up

<Mermaid
  caption="Inside the container. The router starts immediately; everything that touches data waits."
  chart={`
flowchart TB
  ep["entrypoint.sh<br/>read plan, compute environment,<br/>write router config + service list"]
  ep --> init["hand over to the supervisor"]
  init --> cad["router<br/>starts immediately"]
  init --> dbs["database server<br/>(only if the project needs one)"]
  init --> minio["object storage"]
  init --> deps["dependency seeding"]
  dbs --> dbi["db-init<br/>restore, migrate, fixtures, buckets"]
  minio --> dbi
  deps --> dbi
  dbi --> svc["the project's backends<br/>and dev servers"]
`}
/>

The database restore and the project's own migrations run here. **A failed migration does not
stop the sandbox.** The failure is recorded, the sandbox reports itself `degraded`, and
everything boots anyway — because inspecting a failed migration is one of the main reasons the
sandbox exists.

<Detail kind="why" summary="why the router does not wait for the database">

A first-boot restore legitimately takes minutes, and that is exactly when you most need to know
what is going on.

If the router waited, the whole sandbox would answer "connection refused" for the whole of its
first boot — and a refused connection is not an answer. You cannot tell a slow restore from a
broken one. So the router starts straight away and serves two things that do not touch the
database: the status pages, and the "not built yet" page.

A backend that is not up yet answers **502**, and a 502 is truthful: *I am here, that service is
not.*

The tool sandboxr generalises did gate its router on the database, and its sandboxes were
unreachable and unexplained for the whole of their first boot.

</Detail>

## Step 8 — you get URLs

Every app and API the project declares gets a hostname of its own:

```
https://feat-123.app.acme.sbx.lcl      the main app
https://feat-123.api.acme.sbx.lcl      the API behind it
https://feat-123.admin.acme.sbx.lcl    the admin app
https://sbx.lcl                        the dashboard, for every sandbox on the machine
```

Read a sandbox hostname as `<slug>.<label>.<project>.<domain>`.

Open the app URL now and you will probably see a page saying it has not been built yet, naming
the command that builds it. That is not a failure. Front-ends are built **on demand**, never at
startup, because a sandbox has to come up in seconds and you usually only care about one of them.

```bash
sandboxr reload --web app
```

## Step 9 — you work

Save a file. It is inside the container immediately, because of the bind mount. Nothing is
rebuilt by that, so you rebuild the thing you touched:

```bash
sandboxr reload --go api      # rebuild one backend and restart it
sandboxr reload --web app     # rebuild one front-end
sandboxr reload --migrate     # re-run this sandbox's migrations
```

Details and costs: [the edit–reload loop](/use/edit-and-reload/).

## Step 10 — a request arrives

Somebody opens `https://feat-123.app.acme.sbx.lcl`.

1. DNS sends the whole domain suffix to the machine running sandboxr.
2. A **shared router** — one for the whole machine — terminates HTTPS, reads the hostname, and
   forwards to the right container. It never looks at the path.
3. Inside that container, a second router reads the same hostname, matches it against the app
   labels in the plan, and either serves files from the built directory or forwards to a service
   on a local port.

Two routers, because the outer one's job is "which sandbox" and the inner one's job is "which app
inside it". Full detail: [how a request arrives](/architecture/request-path/).

<Aside type="caution" title="The outer router is not built yet">
`packages/core` labels each container `sandboxr.router=true` so a router can find it, but no code
in this repository starts, configures or reconciles a machine-wide router today. That piece is
still to be written.
</Aside>

## Step 11 — you throw it away

```bash
sandboxr down feat-123
```

That removes the container, its database, its object storage and its built artefacts. Because
the database lives *inside* the container, there is no shared schema left behind for somebody to
find next month and wonder about.

It does not remove your worktree, your commits, or the logs in `~/.sandboxr/logs/`.

## What survives what

| Action | Container | Database | Storage | Built apps | Worktree | Logs |
|---|---|---|---|---|---|---|
| `sandboxr reload` | kept | kept | kept | rebuilt | kept | kept |
| `sandboxr up` again | replaced | kept | kept | kept | kept | kept |
| `sandboxr down` | removed | **removed** | **removed** | **removed** | kept | kept |
| `sandboxr down --keep` | removed | kept | kept | kept | kept | kept |
| `sandboxr gc` | removed | **removed** | **removed** | removed | already gone | kept |

<Detail kind="failure" summary="the five points in this sequence that go wrong, and what each looks like">

| Where | Symptom | Cause |
|---|---|---|
| Step 3 | `up` refuses and names a config field | The project serves public apps and would carry real data or real credentials. Working as designed. |
| Step 4 | The database will not start, reporting a corrupt data file | Almost always a **full Docker disk**. Check `docker system df` before believing anything else a failing database says. |
| Step 7 | The sandbox is `degraded` | The project's migrations failed. Intended: the sandbox stays up so you can inspect it. `sandboxr logs <slug>`, then `sandboxr db shell <slug>`. |
| Step 8 | Nothing resolves at all | DNS, not sandboxr. There is no outer router yet either — see the note in step 10. |
| Step 9 | A front-end build dies with `code 137` | The kernel killed it for memory. `137` is `128 + 9`. Declare `memory:` on that app. |

Everything else: [symptom to cause](/troubleshooting/symptom-to-cause/).

</Detail>
