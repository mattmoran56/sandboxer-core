There are four separate places files live, and mixing them up is the most common way to get lost.

| Place | What it holds | Who owns it |
|---|---|---|
| **The sandboxr repository** | The tool itself | Whoever works on sandboxr |
| **Your project's repository** | One settings file, `sandboxr.yaml` | The project's team |
| **`~/.sandboxr` on your computer** | Caches, logs, certificates, secrets | sandboxr, at run time |
| **Inside a running container** | The project's code, its database, its built output | The sandbox, and thrown away with it |

## 1. The sandboxr repository

<FileTree>
- packages/
  - core/ **@sandboxr/core** — settings, drivers, Docker, lifecycle
    - src/
      - config/ reading `sandboxr.yaml`, and writing `plan.json`
      - drivers/ one module per kind of database
      - sandbox/ up, down, list, status, reload, gc
      - naming.ts every name in the system is decided here
      - paths.ts every host path is decided here
      - secrets.ts reading `.env` files safely
  - cli/ **@sandboxr/cli** — the `sandboxr` command
  - server/ **@sandboxr/server** — the dashboard, auth, terminal
  - docs/ this site
- container/ what runs **inside** a sandbox
  - base/ the generic base image
  - project/ the per-project layer template
  - scripts/ the shell scripts a sandbox runs
  - examples/ two worked `plan.json` files
- docs/
  - architecture/
    - **contracts.md** the single source of truth for every boundary
- examples/ two worked `sandboxr.yaml` files
</FileTree>

Two files outrank everything else. `docs/architecture/contracts.md` defines every boundary in the
system; `container/README.md` defines everything inside a sandbox, including the exact shape of
`plan.json`.

| What does the container do at boot? | `container/scripts/entrypoint.sh` |
| How is a database seeded and migrated? | `container/scripts/db/<driver>.sh` |

</Detail>

## 2. Your project's repository

One file, at the repository root:

```
your-project/
  sandboxr.yaml     ← the whole configuration, versioned with the code
```

It lives with the project rather than with sandboxr so that a new service and the settings that
describe it land in the same commit. Field-by-field:
[sandboxr.yaml](/config/sandboxr-yaml/).

## 3. On your computer

Everything sandboxr writes at run time is under one directory, `~/.sandboxr`.

<Aside type="note" title="Never inside a repository">
`git clean -xdf` is a normal thing to run, and it would destroy the seed cache, the certificate
and every sandbox's logs. So the state directory is deliberately outside every repository.
</Aside>

| Path | What it holds | Survives `down`? |
|---|---|---|
| `~/.sandboxr/cache/` | Database seed artifacts, named by content | yes |
| `~/.sandboxr/logs/<project>/<slug>/` | Per-sandbox logs | **yes** — deliberately |
| `~/.sandboxr/tls/` | The certificate and key the router serves | yes |
| `~/.sandboxr/state/` | Router config, and the dashboard's session key | yes |
| `~/.sandboxr/secrets/<project>.env` | Third-party credentials, mode 0600 | yes |
| `~/.sandboxr/build/<project>/<slug>.env` | The generated environment for one sandbox | yes |
| `~/.sandboxr/build/<project>/<slug>.plan.json` | The plan for one sandbox | yes |
| `~/.sandboxr/bin/` | Helper binaries built on the host | yes |

The logs surviving is on purpose: the logs from a sandbox you have just deleted are usually
exactly the ones you want.

<Detail summary="how to move it, and the one variable that does it">

`SANDBOXR_HOME` overrides the root. Everything else is derived from it, in
`packages/core/src/paths.ts`, so there is no second variable to set.

```bash
export SANDBOXR_HOME=/var/lib/sandboxr
```

On a server, set this **in the service definition**, not in a login shell. A service started at
boot has no login shell, and falling back to `~/.sandboxr` under a service account puts the state
somewhere nobody looks.

The dashboard reads the same variable, and keeps its session-signing key at
`$SANDBOXR_HOME/state/session.key`, mode 0600.

</Detail>

## 4. Inside a running sandbox

| Path | What it is |
|---|---|
| `/workspace` | Your worktree, mounted read and write |
| `/sandboxr/plan.json` | The plan, read-only |
| `/sandboxr/scripts/` | The sandboxr scripts |
| `/sandboxr/cache/` | The host's seed cache, read-only |
| `/var/lib/sandboxr/data` | The database |
| `/var/lib/sandboxr/blob` | Object storage |
| `/var/lib/sandboxr/bin` | Compiled backends |
| `/srv/www` | Built websites, one directory per app label |
| `/var/log/sandboxr` | Per-service log files |
| `/run/sandboxr` | Marker files the status page is composed from |
| `/opt/deps` | Dependencies installed into the image, copied out on first boot |

Get in with:

```bash
sandboxr shell feat-123
```

<Detail summary="the naming scheme for every Docker object a sandbox owns">

For a project `acme` and a slug `feat-123`:

| Object | Name |
|---|---|
| Container | `sandboxr-acme-feat-123` |
| Network | `sandboxr` — one, shared by every sandbox on the machine |
| Database volume | `sandboxr-data-acme-feat-123` |
| Object storage volume | `sandboxr-blob-acme-feat-123` |
| Built binaries volume | `sandboxr-bin-acme-feat-123` |
| Built websites volume | `sandboxr-www-acme-feat-123` |
| Shared dependencies | `sandboxr-deps-<16 hex chars of the lockfile hash>` |
| Shared Go caches | `sandboxr-gocache`, `sandboxr-gomod` |

The dependency volume is keyed on the lockfile rather than on the sandbox, so every sandbox with
the same dependencies shares one install, and a branch that changes its dependencies transparently
gets its own.

Contract §3.3. Code: `packages/core/src/naming.ts`.

</Detail>

## What is *not* stored anywhere

There is no list of sandboxes. No manifest file, no database of what exists.

Everything sandboxr knows about a running sandbox is read from **Docker container labels** at the
moment you ask. `sandboxr ls` is a function of `docker ps` and nothing else, so there is no second
copy of the truth that can drift out of date.
