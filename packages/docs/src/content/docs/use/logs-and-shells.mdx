## Logs

```bash
sandboxr logs feat-123              # everything, interleaved
sandboxr logs feat-123 api          # one service
sandboxr logs feat-123 api -f       # follow
sandboxr logs feat-123 db-init      # the database provisioning run
```

Service names are the `name` values from `backends.services`, plus the internal services the
container runs itself. `db-init` is the one worth remembering: it is where seeding, migration
and fixture output goes, and it is the first place to look when a sandbox comes up
`degraded`.

Logs are written to `~/.sandboxr/logs/<project>/<slug>/` on the host, **outside** the
container. They survive `sandboxr down`, which is deliberate — the logs from a sandbox you
have just deleted are usually the ones you want.

<Aside type="tip" title="Why the log path is outside any repository">
`SANDBOXR_HOME` defaults to `~/.sandboxr` and is never inside a repo, so `git clean -xdf`
cannot destroy your logs, your seed cache or your certificate.
</Aside>

## A shell inside

```bash
sandboxr shell             # the current worktree's sandbox
sandboxr shell feat-123    # a named one
```

You land in `/workspace` — the bind mount of your worktree — with the project's toolchain on
`PATH` at the versions `toolchain:` declares. Anything you build or edit here is happening in
your worktree, so:

```bash
$ sandboxr shell
sandbox:/workspace$ go build ./services/api
sandbox:/workspace$ exit

$ git status
	modified:   services/api/handler.go
```

That is the same property agents rely on. It also means `rm -rf` in a sandbox shell deletes
files from your branch. The container is disposable; the mount is not.

A database shell is separate, because it needs the driver's own client:

```bash
sandboxr db shell          # an interactive client against this sandbox's database
```

## The browser terminal

The dashboard offers a terminal inside any sandbox, at:

```
https://sbx.lcl/p/acme/s/feat-123/terminal
```

Note the shape: it is a **route inside the dashboard**, not a hostname of its own. That is a
deliberate constraint rather than an implementation detail.

- It inherits the dashboard's session, so it is behind the password automatically. There is
  no second auth mechanism to get wrong.
- It **cannot** be exposed on a public app hostname, because it is not on one. A terminal on
  a per-sandbox hostname would be one config mistake away from being a public shell on your
  Docker host.

The terminal is a WebSocket, because it is bidirectional. Everything else the dashboard
streams — a build, a migration — is Server-Sent Events, which is one-way and simpler. See
[design decisions](/architecture/decisions/#actions-stream-over-two-transports-not-one).

## What the dashboard does

The dashboard lists every sandbox on the machine, reading container labels live, so it cannot
disagree with what is actually running. Per sandbox it shows the branch, the pull request if
there is one, a tile per app, which backends are up, and whether the migration succeeded.

Each action opens a panel that streams the command's output as it happens, with elapsed time
and a progress bar. The bar is a **real fraction** wherever the output carries one — a
migration reports its own count, a bulk rebuild announces its list — and an honest
indeterminate bar where it does not, rather than an invented percentage. Closing the panel
does not stop the action.

Typical actions:

| Action | Equivalent |
|---|---|
| Open an app | the app's hostname |
| Rebuild an app | `sandboxr reload --app <label>` |
| Rebuild front-ends | `sandboxr reload --app built` |
| Run migrations | `sandboxr db migrate` |
| Re-apply fixtures | part of `sandboxr db reset` |
| Restart | `sandboxr restart <slug>` |
| Reset the database | `sandboxr db reset` — asks first |
| Delete the sandbox | `sandboxr down <slug>` — asks first |
| Terminal | the route above |
| Start a sandbox from a pull request | `sandboxr ensure <branch>` |

The last two rows in the destructive group ask for confirmation, because they cannot be
undone. Everything else is idempotent.

<Aside type="danger" title="Every one of these is behind the password">
There is no unauthenticated action endpoint, not one. The dashboard drives Docker, so an open
action endpoint is remote code execution on the host. The actions are also a **closed table**
in the server — there is no generic "run this command" endpoint to find.
[Why, in full](/security/two-tiers/).
</Aside>

## Why the dashboard runs the real CLI

The dashboard's buttons shell out to the same `sandboxr` code path the CLI uses, rather than
reimplementing start, stop and rebuild in the web server.

That logic carries a lot of hard-won detail — volume names keyed on a lockfile hash, seed
cache invalidation, healing stuck migration bookkeeping — and a second implementation would
have drifted from the first within a week. One consequence is worth knowing: **the dashboard
is only as reliable as the code it reads.** While a source file is half-saved, every button
fails in whatever way that file happens to fail. A dashboard should recognise its own
toolchain's diagnostics and say "the CLI is mid-edit or broken" rather than reporting a
mystery.

## Choosing between them

| You want to | Use |
|---|---|
| See why a service is crash-looping | `sandboxr logs <slug> <service> -f` |
| See why the database is not what you expected | `sandboxr logs <slug> db-init`, then `sandboxr db diff` |
| Run a one-off build or poke at files | `sandboxr shell` |
| Query the database | `sandboxr db shell` |
| Do any of the above from a machine that is not yours | the dashboard terminal |
| Give a reviewer a way to restart something | the dashboard |
