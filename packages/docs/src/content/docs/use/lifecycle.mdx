The whole daily surface, in one block:

```bash
cd .worktrees/feat-123
sandboxr up                     # start a sandbox from this worktree
sandboxr list                   # every sandbox on this machine
sandboxr logs feat-123 api -f   # tail one service
sandboxr shell                  # a shell inside, with the toolchain on PATH
sandboxr down feat-123          # remove it, and its database and storage
sandboxr gc                     # reap sandboxes whose worktree is gone
```

The slug defaults to the worktree directory name, so most commands need no argument when you
are standing in the worktree.

<Aside type="caution" title="Derived, not verified">
`list` and `gc` are named in the contract. The rest of this page follows the tool sandboxr
generalises and has not been run against sandboxr itself. See
[what is built](/reference/status/).
</Aside>

## Starting

```bash
sandboxr up
```

About 30 seconds with a warm seed cache. What happens in that time is on
[your first sandbox](/start/first-sandbox/#what-the-first-thirty-seconds-do).

Two flags matter often enough to know:

```bash
sandboxr up --with cms          # also start an app marked `optional: true`
sandboxr up --memory 8g         # raise the per-sandbox memory limit for this run
```

`--with` exists because some things are too expensive to run by default. A live dev server
holds hundreds of megabytes for as long as the container lives, whether or not anyone opens
it — so an app declared `optional: true` starts only when you ask.

Starting a sandbox that already exists is not an error; it reconciles the running container
with the config. That is what makes `up` safe to re-run after changing `sandboxr.yaml`, and
it is the command you need after a **dependency change**, because the shared `node_modules`
volume is keyed on the lockfile.

## Listing

```bash
sandboxr list
```

```
SLUG        PROJECT   BRANCH              STATE      APPS BUILT     AGE
feat-123    acme      feat-123            running    app, api       12m
fix-nav     acme      fix/nav-overflow    degraded   app            2h
docs-pass   acme      docs/rewrite        running    –              4d
```

This is a **pure function of `docker ps`**. There is no manifest file and no database of
sandboxes; every column comes from a container label. Nothing can drift out of sync, because
there is no second copy of the truth to drift from. See
[state lives in labels](/architecture/state/).

`degraded` means the container is up but its migration failed. The services are running and
you can get a shell — deliberately, because inspecting a failed migration is one of the
reasons the sandbox exists.

## Restarting

```bash
sandboxr restart feat-123
```

Restarts the supervised processes without touching the database or re-running migrations.
Use it when a service has wedged. If you want the migration to run again, that is
[`sandboxr db migrate`](/databases/testing-a-migration/), not a restart.

<Aside type="tip" title="If a restart does not seem to take effect">
A supervised process that is *piped* rather than `exec`'d survives a restart and keeps
holding its port, so every replacement dies with `address already in use` while the old code
carries on serving. The symptom is "my change did nothing" and the cause is a run script.
[The full explanation](/troubleshooting/symptom-to-cause/#a-restart-changed-nothing).
</Aside>

## Deleting one

```bash
sandboxr down feat-123
```

That removes:

- the container, `sandboxr-acme-feat-123`
- its database volume, `sandboxr-data-acme-feat-123`
- its object-storage volume, `sandboxr-blob-acme-feat-123`
- its built binaries and built sites, `sandboxr-bin-…` and `sandboxr-www-…`
- its hostnames, from the shared router

It does **not** remove:

- **the worktree on disk**, so deleting a sandbox never loses work
- the shared `node_modules` volume, which other sandboxes on the same lockfile are using
- the shared Go module and build caches
- `~/.sandboxr/logs/acme/feat-123/`, which survives the container on purpose — the logs from
  a sandbox you have just deleted are usually the ones you want

Because the database lives *inside* the container, `down` really does remove everything
about it. There is no shared schema left behind for someone to find next month and wonder
about.

## Cleaning up in bulk

```bash
sandboxr gc              # sandboxes whose worktree no longer exists
sandboxr gc --merged     # also those whose pull request is merged
sandboxr gc --dry-run    # say what it would do
```

`gc` is safe by construction: it reads the `sandboxr.worktree` label, checks whether that
path still exists, and removes the sandbox if it does not. A sandbox whose worktree you
deleted is unreachable — you cannot rebuild anything in it — so it is pure waste.

`gc` also **prunes Docker's build cache**, which is the fastest-growing thing in this whole
system and which nothing else cleans up. If you are tight on disk, this is the command.

<Aside type="note" title="`--merged` needs `gh`">
Deciding whether a branch's pull request is merged is an authenticated API call, so it runs
host-side with `gh`. Without `gh` authenticated, `gc --merged` degrades to plain `gc` and
says so.
</Aside>

## A day, end to end

<Steps>

1. **Morning.** `sandboxr list` to see what survived yesterday. `sandboxr gc --dry-run` if
   the machine feels full.

2. **Pick up a ticket.** `sandboxr ensure feat-456` — finds or creates a worktree for the
   branch and brings a sandbox up in one command.

3. **Work.** Edit in the worktree, `sandboxr reload --backend api`, refresh. The loop and its
   costs are on [the edit–reload loop](/use/edit-and-reload/).

4. **Send it to someone.** The app hostname is a real HTTPS URL. If the project's apps are
   `public`, that is all you need to do.

5. **Something is wrong and the logs are not enough.** `sandboxr shell`, or the terminal in
   the dashboard. [Logs, shells and terminals](/use/logs-and-shells/).

6. **Done with it.** `sandboxr down feat-456`. The worktree and its commits stay.

</Steps>

## What survives what

| Action | Container | Database | Storage | Built apps | Worktree | Logs |
|---|---|---|---|---|---|---|
| `restart` | restarted | kept | kept | kept | kept | kept |
| `up` again | reconciled | kept | kept | kept | kept | kept |
| `reload` | kept | kept | kept | rebuilt | kept | kept |
| `db reset` | kept | **re-seeded** | kept | kept | kept | kept |
| `down` | removed | **removed** | **removed** | removed | kept | kept |
| `gc` | removed | **removed** | **removed** | removed | already gone | kept |

The only row that destroys data you might want is `db reset`, and it is the row you reach for
deliberately when [testing a migration](/databases/testing-a-migration/).
