## Your changes are already inside

The worktree is **bind-mounted** into the sandbox at `/workspace`. Saving a file on your
machine puts it in the container immediately. There is no push, no sync, no copy step, and
nothing to remember.

It works in the other direction too: a process editing inside the container — a coding agent,
or you in `sandboxr shell` — writes to your worktree, so its changes appear in `git status`
and you commit them normally. That is the whole basis of
[agents in a sandbox](/agents/in-a-sandbox/).

What a bind mount does *not* do is rebuild anything. A Go binary is a binary; a bundled
single-page app is a directory of hashed files. Applying a change means rebuilding the thing
you touched.

## The commands and what they cost

```bash
sandboxr reload --backend api      # one backend
sandboxr reload --backend          # every backend
sandboxr reload --app app          # one front-end, by label
sandboxr reload --app all          # the project's main front-ends
sandboxr reload --app built        # everything this sandbox has already built
sandboxr up                        # after a dependency change
```

| Command | What it covers | Cost |
|---|---|---|
| `reload --backend <name>` | one backend: compile, replace the binary, restart the service | ~2s |
| `reload --backend` | every backend the config declares | ~2s |
| `reload --app <label>` | one front-end bundle | ~3s |
| `reload --app <label>` (component library) | a static component-library build | ~25–45s |
| `reload --app all` | the project's main single-page apps | ~9s |
| `reload --app built` | exactly what this sandbox has already built | ~9s, or ~35s once a component library is in it |
| `up` | a dependency change — reseeds or rebuilds the `node_modules` volume | ~30s |

<Aside type="caution" title="Measured elsewhere">
These are measurements from one large monorepo using the predecessor tool, not from
sandboxr. Treat them as the right order of magnitude and nothing more. See
[what is built](/reference/status/).
</Aside>

## `all` and `built` are not the same thing, on purpose

This distinction saves real time, and it is not obvious.

**`all`** means the project's main single-page apps and nothing else. It deliberately
excludes the expensive members of `frontends.apps` — a marketing site that renders thousands
of pages, a component library — because a file-watcher calls `all` on any front-end change,
and widening it would start a multi-gigabyte site build as a side effect of a component
tweak. An app opts out of `all` with `in_build_all: false`.

**`built`** reads what this sandbox has actually built and refreshes exactly that. Once you
have built the marketing site in a sandbox, `built` includes it; in a sandbox where you never
did, it does not. It never *starts* a first build of an expensive app — that is an explicit
act — and with nothing built yet it falls back to `all`.

So: `all` is "the usual four, fast". `built` is "everything this sandbox actually serves".

## There is no hot reload

The loop is **edit, reload, refresh**. This is a trade, made deliberately, and it is worth
understanding rather than working around.

A dev server per app per sandbox would hold hundreds of megabytes resident for the life of
the container, whether or not anyone ever opens that app. The point of sandboxr is running
*several* sandboxes at once under one memory limit, so that cost is paid many times over for
something consulted occasionally. A static build costs a few seconds when you ask for it and
nothing at all when you do not.

Where you genuinely need hot reload — iterating on one component's styling — the right answer
is to run that one app's dev server on your machine, against the sandbox's API, and keep the
sandbox for the integration.

The exception is a `serve:` front-end, which *is* a long-running dev server and does hot
reload. That is what [the third runtime kind](/config/runtime-kinds/) exists for, and it is
why such apps are usually declared `optional: true`.

## Memory limits

The per-sandbox default is 2 GB. Backends and single-page apps do not come close. A static
site generator rendering a few thousand pages will blow straight through it, and the way it
fails is the problem:

<Tabs>
<TabItem label="The symptom">

```
> marketing@1.0.0 build
> next build

  ▲ Next.js 15.0.0
   Creating an optimized production build ...
   Collecting page data ...
Killed
npm ERR! Lifecycle script `build` failed with error:
npm ERR! code 137
```

Nothing in that output mentions memory. `code 137` is `128 + 9` — the process was killed by
`SIGKILL` — and it reads like a broken build rather than a full one. People go and debug
their own code.

</TabItem>
<TabItem label="The cause">

A static site generator spreads page rendering across many worker processes. No single
`--max-old-space-size` bounds it, because no single process is the problem: the **cgroup
total** is what the kernel measures and what the OOM killer acts on.

A build that dies at 2 GB will also die at 4 GB, part-way through a later phase, in exactly
the same way.

</TabItem>
<TabItem label="The fix">

Declare what the app actually needs, in the config, so the sandbox is created with the right
limit:

```yaml
frontends:
  apps:
    - label: www
      package: marketing
      build: npm run build
      out: out
      memory: 6g
```

Or raise it for one run:

```bash
sandboxr up --memory 8g
```

A build script should **refuse up front** when the limit is below what it needs, and print
the limit and the fix. Failing in one second with a named cause beats failing in twenty with
`code 137`.

</TabItem>
</Tabs>

<Aside type="danger" title="Under memory pressure, the kernel does not pick politely">
On a machine with several sandboxes running, a heavy front-end build gets *something*
OOM-killed, and that something can be another sandbox — or your own local database container.
Before a big build, stop the sandboxes you are not using.
</Aside>

## When `reload` is not enough

| Situation | What to run |
|---|---|
| Changed a lockfile or added a dependency | `sandboxr up` — the `node_modules` volume is keyed on the lockfile hash |
| Changed `sandboxr.yaml` | `sandboxr up` — it reconciles the container with the config |
| Added a migration | `sandboxr db migrate`, then `sandboxr db diff` |
| Changed a toolchain version | `sandboxr image build` — the project layer, not the shared base — then `sandboxr up` |
| A service is wedged and the code is fine | `sandboxr restart` |
| The database is in a state you no longer trust | `sandboxr db reset` |
