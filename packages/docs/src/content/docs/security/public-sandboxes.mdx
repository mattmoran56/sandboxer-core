**Read this page before you point a DNS record at a sandboxr host.** If you only skim one
thing, skim the two conditions.

If `access.apps` is `public`, sandboxr **refuses to start** unless both of these hold:

1. **The database seed is fixtures, or a dump explicitly marked as anonymised.** Never a fork
   of a live database.
2. **Third-party credentials are dummies**, unless explicitly opted in.

`access: private` is the escape hatch. There is no third option and no override flag.

## Condition 1: the seed

A public URL backed by real records is a data leak. Not a risk of one — an actual one, the
moment the URL is reachable.

It does not matter that the app requires login, because:

- A sandbox is running unreleased code, which is exactly the code whose authorisation checks
  are least reviewed.
- Fixtures usually include accounts with known passwords, and a fork of live data plus a
  fixture login is a login to real data.
- An API on a public hostname is a public API. Every endpoint the front-end does not call is
  still there.
- Search indexers find hostnames. So do certificate transparency logs, which publish every
  name you issue a certificate for.

So: on a public deployment, seed from fixtures, or from a dump that somebody has actually
anonymised.

```yaml
database:
  seed_from:
    # No `local:` — a fork of a live database is refused for a public project.
    file: /var/sandboxr/seeds/acme-anonymised.sql.zst
    fixtures: db/seeds/fixtures.sql
```

<Aside type="caution" title="How a dump is marked anonymised is not specified yet">
The contract requires an "explicitly-marked anonymised dump" but defines no field that marks
one, and neither example config has one. Until the schema lands, the safe reading is: a public
project should have **no `local:` block at all**, and you should be able to say who anonymised
the dump in `seed_from.file` and how. Recorded on [what is built](/reference/status/).
</Aside>

### "Anonymised" means anonymised

Worth being blunt, because this is where the requirement gets quietly downgraded:

- Nulling a `name` column while leaving `email` is not anonymisation.
- Hashing an email is not anonymisation if the hash is reversible by guessing — and email
  addresses are extremely guessable.
- Free-text fields carry personal data. Support notes, feedback, addresses typed into a
  "notes" box, AI-generated summaries about a person.
- Filenames and object-storage keys carry personal data. So do URLs.
- A "test" account with a real customer's data in it is a real customer's data.

If you cannot describe the anonymisation in one sentence and defend it, use fixtures.

## Condition 2: credentials

Anyone who can drive a public app can make it do whatever the app does. If the app's
credentials are real, that includes:

| The app can | So a stranger can |
|---|---|
| Send transactional email | Send email from your domain, to real addresses |
| Call an LLM provider | Spend your credit, at whatever rate a script can loop |
| Write to an analytics property | Poison the numbers your team makes decisions on |
| Write to object storage | Put whatever they like in your bucket |
| Call a payment provider | You do not want to finish this sentence |

None of that needs a vulnerability. It is the app working correctly.

So a public sandbox gets dummy credentials, and the sandbox provides its own versions of the
things it can: its database is internal, its object storage is internal, its inter-service
URLs are computed. That is why `S3_*`, `DB_*` and `*_URL` are in
[`secrets.never`](/config/secrets/#anything-describing-where-something-runs-is-never-imported).

<Aside type="caution" title="The opt-in mechanism is also unspecified">
"Unless explicitly opted in" has no field yet either. Assume a public project needs dummy
values, and use `access.apps: private` when it genuinely needs real ones.
</Aside>

## Why refusals, not warnings

This is the part worth arguing with, so here is the argument.

A warning is a reasonable design when the cost of ignoring it is bounded and recoverable. You
see the warning, you weigh it, you proceed, and if you were wrong you fix it.

Neither of these failures is recoverable:

- **A data leak cannot be un-leaked.** Once real records have been served to the internet you
  do not know who fetched them, and you have a disclosure obligation whatever you do next.
- **Spend cannot be un-spent**, and email cannot be un-sent. A stranger looping a request that
  triggers an LLM call can produce a bill overnight.

And warnings fail in exactly the situation that matters. They are printed during `up`, which is
a command you run dozens of times a day, mostly while thinking about something else. They
scroll. They get filtered out of CI logs. They become familiar, and familiar warnings are
invisible.

A refusal is the only mechanism that is still working at 6pm on a Friday when someone is
setting up a demo in a hurry.

<Aside type="danger" title="The escape hatch is a config change, and that is the point">
`access.apps: private` is one line, and it is a line that ends up in a diff with a reviewer
looking at it. That is the difference between a deliberate decision and a warning nobody read.
</Aside>

## A pre-flight checklist for a public deployment

Run through this before the DNS record exists.

- [ ] `access.apps` is `public` **only** on projects where that is genuinely intended.
- [ ] No `seed_from.local` on the server. There is no local container to fork, and pointing it
      at a production database is the exact mistake the driver contract exists to prevent.
- [ ] The dump in `seed_from.file` is anonymised, and you can say by whom and how.
- [ ] `secrets.keep` contains only names whose values are dummies on this host.
- [ ] `secrets.never` covers `DB_*`, `S3_*`, `*_URL`, and anything else describing location.
- [ ] `SANDBOXR_PASSWORD` is set, long, random, and not in a shell history file.
- [ ] Only ports 80 and 443 are open. The Docker socket is not exposed over TCP.
- [ ] The certificate is a real one, not the local development CA.
- [ ] Your identity provider's allowlists have the wildcards, on a **development-only**
      application — never the one production uses.
- [ ] You have opened the dashboard from a private browser window and confirmed it asks for the
      password.
- [ ] You have opened an app hostname from a private browser window and confirmed you see what
      you expect a stranger to see.

Those last two take a minute and catch the mistakes that reading configuration does not.

## If the project needs real data

Use `access.apps: private`. The apps then sit behind the same session as the dashboard, and the
seed and credential requirements do not apply — because there is no longer a public URL over
real records.

You lose the ability to send someone a link without giving them the password. That is the
actual trade, and it is the right one whenever the data is real.
