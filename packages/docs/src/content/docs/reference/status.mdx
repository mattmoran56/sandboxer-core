These docs were written from `docs/architecture/contracts.md`, the settled design, while the
code was still being written. Some of that code now exists. This page says exactly which
claims on this site are measurements, which are specifications, and which are proposals, so
you never have to guess.

<Aside type="danger" title="No end-to-end run has ever happened">
**No project has ever been booted in a sandbox.** The container layer exists and its generic
base image builds and boots, but no per-project image layer has ever been built, no backend has
ever been compiled or run, and no `sandboxr` command has been executed against a real project.

Every command on this site is transcribed from the contract or carried over from the internal
single-repo tool sandboxr generalises. Treat commands as the intended interface, not as verified
behaviour.
</Aside>

## What has actually been run, in `container/`

These were exercised against the base image, hand-written plans and stub commands:

- `bash -n` and `shellcheck -x -S warning` are clean across every script.
- Both example plans generate an s6 service tree and a router config, and both generated
  Caddyfiles pass `caddy validate`.
- Served for real: a built app serves; a deep path falls back to `index.html`; an unbuilt app
  answers 503 with instructions; `/__sandboxr/live` answers 200 on any hostname; an unknown
  host answers 404 naming the host.
- The database-init → migrate → status chain produces the right state for each outcome: no
  migration command → `ok`/`skipped`; a failing command → `degraded`/`failed` with the file and
  error extracted; a command that exits zero while printing its own failure summary →
  `degraded`, via `failure_pattern`; a clean run → `ok`.
- The static builder refuses a declared `memory:` the container cannot meet, and builds and
  swaps in a directory when it can.
- The project Dockerfile template renders lint-clean (`docker build --check`) for three block
  combinations: Go+Node+MySQL, Node+SQLite, and Go alone.
- The base image builds (~400 MB, glibc 2.36) and boots: s6 compiles the generated tree, the
  ungated services start, database init runs the driver dispatch and provisions buckets, an
  on-demand build lands in the web root and is served through the generated router, and every
  computed and aliased environment variable reaches each supervised service.

## What is written but has never run

| Area | What a real run would settle |
|---|---|
| The project image layer | It renders lint-clean and has **never been built**. Every download in it is unproven: the Go and Node index queries, the MySQL tarball URL for a real series, the `sqlite3` and `libaio1` installs. |
| Toolchain resolution | That a prefix such as `1.26` or `24` picks the release a project meant, on both architectures. |
| MySQL | Data-directory initialisation, the app user and grants against a live server, restoring a real dump, and the schema snapshot. |
| Dependency seeding | The seed from the image's install path, the lockfile-hash mismatch that falls back to a real install, and the workspace bin re-linking. |
| `d1` / `sqlite` | Provisioning from real miniflare state, locating the SQLite file by glob, and whether the `owner` rule actually prevents the deadlock it exists to prevent. |
| The s6 graph under load | It boots for a two-service plan. Five backends, a dev server and a first-boot restore have not been started together. |
| Backends | None has been built or run. The staleness check and the build-failure pause are untested against a real compiler. |

Nothing in that list is expected to be *structurally* wrong. All of it is expected to have at
least one thing wrong in the details.

## What does not exist at all

Documented on this site as intent, and it is worth being blunt about which:

- **Real remote deployment.** Wildcard DNS, ACME certificates over DNS-01, and running the
  dashboard as a service on a host. No code requests a certificate, writes a DNS record or
  installs a service unit. [The deployment guide](/server/deployment/) is a plan.
- **A coding-agent service.** sandboxr does not install, declare or supervise an agent inside a
  sandbox. [That page](/agents/in-a-sandbox/) describes running your own agent against the bind
  mount, which is a way of working rather than a feature.
- **The CLI.** No command on [the CLI page](/reference/cli/) exists. The contract does not pin a
  CLI surface at all — §3.4 names `list` and `gc`, and nothing else is specified.
- **The dashboard and its action table.** Contract §8 requires a closed table of actions; its
  contents are not specified anywhere and the server package is unwritten.
- **Per-project access control.** Contract §7 says a password grants the projects it is
  configured for. There is one `SANDBOXR_PASSWORD` and no mapping from passwords to projects.

## Gaps still open in the contract

Each of these is a documentation bug worth fixing in `contracts.md`, recorded here rather than
papered over.

1. **§5's YAML snippet does not parse.** `backends:` is shown as a block sequence with a
   `defaults:` mapping key as a sibling of the list items, which is invalid YAML. The example
   configs use `backends: { defaults, services }` and `frontends: { root, defaults, apps }`.
   These docs follow the examples and say so on
   [the schema page](/reference/config-schema/).
2. **`seed_from.local` and `seed_from.file` can both be set, and precedence is not stated.**
   The example's comments imply "local on a laptop, file on a server", but nothing says which
   wins when both are present, or whether the choice is environmental or ordered. Documented as
   unspecified.
3. **§5.3 requires an "explicitly-marked anonymised dump" and `sandboxr.yaml` has no field that
   marks one.** `plan.json` does carry `database.seed.anonymised`, so the container side of the
   boundary exists — but nothing in the config schema produces it, and §5.3's refusal has
   nothing to read.
4. **"Unless explicitly opted in" for third-party credentials has no opt-in field.** Documented
   as an open question on [public sandboxes](/security/public-sandboxes/).
5. **§5.3's first condition is ambiguous.** "The database seed is a fixture" is hard to read
   against a `seed_from` block where `fixtures` is applied *after* migrations and coexists with
   `local`/`file`. The reading these docs use — a public sandbox may have no `local` fork, and a
   `file` only if marked anonymised — is stated as an interpretation.
6. **No CLI surface is defined.** §3.4 names `list` and `gc`; §8 says actions are a closed table
   in the server package but does not enumerate it.
7. **`degraded` is a state with no home.** §6 says a failed migration marks a sandbox
   `degraded`, and the container derives it from marker files into `status.json` — but §3.4's
   label table has no field for it, and §3.4 says state lives *only* in labels. Either a label
   is missing or the contract should say the sandbox's own status surface is the authority.
8. **The per-project access model in §7 has no configuration.** "A password grants the projects
   it is configured for" — there is one `SANDBOXR_PASSWORD` and no file mapping passwords to
   projects. Documented as intent.

Not on that list, because §5.4 and §5.5 specify them: `storage`, `static_mode`,
`in_build_all`, `database.owner`, `SANDBOXR_MIGRATE_SINCE`, the `--persist-to` requirement for
file-backed drivers, and `plan.json` as a named boundary with an authoritative shape.
