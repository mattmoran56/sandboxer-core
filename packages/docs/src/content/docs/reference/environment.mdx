## From the contract

These three are defined in `contracts.md` and will not change name.

| Variable | Default | What it is |
|---|---|---|
| `SANDBOXR_HOME` | `~/.sandboxr` | Cache, logs, certificates, router state, secrets, generated environments, host-built binaries. Deliberately **never inside a repository**, so `git clean -xdf` cannot destroy it. |
| `SANDBOXR_DOMAIN` | `sbx.lcl` | The hostname suffix. Every app is `<slug>.<label>.<project>.<domain>`; the dashboard is the bare domain. |
| `SANDBOXR_PASSWORD` | *(none)* | The control-plane password. **There is no default and no way to disable the requirement.** Compared timing-safely, stored as a hash, never logged. |

<Aside type="danger" title="`SANDBOXR_PASSWORD` is a root credential for the host">
The dashboard talks to the Docker socket, so whoever has this password can do anything on the
machine. Generate it with `openssl rand -base64 32`, keep it in a secret manager, and keep it
out of shell history. [Why this is not negotiable](/security/two-tiers/).
</Aside>

## Derived

<Aside type="caution" title="Not in the contract">
The names below are derived from the tool sandboxr generalises, to have something concrete to
document. Expect them to change. See [what is built](/reference/status/).
</Aside>

| Variable | Default | What it is |
|---|---|---|
| `SANDBOXR_MEMORY_LIMIT` | `2g` | Per-sandbox memory cap. Overridden per app by `memory:` in the config, and per run by `up --memory`. |
| `SANDBOXR_BASE_IMAGE` | `sandboxr/base:latest` | The shared base image tag. The per-project layer is `sandboxr/<project>:<hash>` and is not overridable — the hash is what makes it correct. |
| `SANDBOXR_CACHE_TTL_HOURS` | `24` | How stale a cached seed artifact may get before it is re-taken, regardless of fingerprint. |
| `SANDBOXR_ACME_EMAIL` | *(none)* | Contact address for ACME certificate issuance. Required on a server. |
| `SANDBOXR_DEBUG` | unset | Verbose tracing. |

Your DNS provider's API token, for the DNS-01 challenge on a server, is read under **the
provider's own variable name** rather than a sandboxr one, because the router's ACME client is
what consumes it.

## Inside the container

These are real: they are read and exported by the container's entrypoint, and every one of
them was observed reaching a supervised service when the base image was booted.

### What the host passes in

| Variable | Default | What it is |
|---|---|---|
| `SANDBOXR_SLUG` | *(required)* | The sandbox's slug. The one variable with no default. |
| `SANDBOXR_PROJECT` | from the plan | The project name. |
| `SANDBOXR_DOMAIN` | `sbx.lcl` | The hostname suffix the router generates its matchers from. |
| `SANDBOXR_WITH` | unset | Comma-separated labels of `optional:` services to start. |
| `SANDBOXR_SEED` | unset | Which cached seed artifact to provision from. |
| `SANDBOXR_DB_USER`, `SANDBOXR_DB_PASSWORD` | defaulted | Credentials the sandbox's own database is created with. |
| `SANDBOXR_S3_KEY`, `SANDBOXR_S3_SECRET` | defaulted | Credentials the sandbox's own object store is created with. |

<Aside type="tip" title="`SANDBOXR_DOMAIN` reaching the router is not a given">
The tool sandboxr generalises hardcoded its domain in thirteen places in a static router
config, so its domain override silently did nothing: every request landed on the catch-all 404
and nothing said why. The router config here is generated from this variable at every boot.
</Aside>

### What the sandbox computes for itself

Derived by the entrypoint and exported to every service. **Never import any of these** — that
is what [`secrets.never`](/config/secrets/) is for.

| Variable | Present when |
|---|---|
| `SANDBOXR_DB_DRIVER`, `SANDBOXR_DB_NAME`, `SANDBOXR_DB_DIR` | always |
| `SANDBOXR_DB_HOST`, `SANDBOXR_DB_PORT`, `SANDBOXR_DB_USER`, `SANDBOXR_DB_PASSWORD` | `driver: mysql` |
| `SANDBOXR_DB_FILE` | `driver: sqlite` |
| `SANDBOXR_D1_DIR`, `SANDBOXR_D1_OWNER` | `driver: d1` |
| `SANDBOXR_S3_ENDPOINT`, `SANDBOXR_S3_KEY`, `SANDBOXR_S3_SECRET`, `SANDBOXR_S3_REGION` | `storage.driver: minio` |
| `SANDBOXR_MIGRATE_SINCE` | `database.migrate.since` is set |
| `SANDBOXR_URL_<LABEL>` | one per app label |
| `SANDBOXR_PORT_<SERVICE>` | one per port-holding service |

Two of these have to be consumed by commands in your config rather than being applied for you:

- **`SANDBOXR_MIGRATE_SINCE`** is exported, not added to your migration command as a flag.
  sandboxr cannot guess a runner's flag spelling, so the command has to reference it.
- **`SANDBOXR_D1_DIR`** must be passed to wrangler's `--persist-to` by **both** the `serve` and
  the `migrate` command for a file-backed driver. Miss it and the runtime writes into the
  worktree instead of the sandbox.

`SANDBOXR_URL_<LABEL>` exists because only the container knows both the slug and the domain at
the moment a build runs. Same-origin API calls do not need it — the router serves `/api` on the
app's own hostname, which keeps the bundle free of cross-origin requests and takes CORS out of
the picture entirely — but cross-app navigation needs an absolute, slug-bearing URL.

The project's own spellings for all of this come from the plan's `env` map, which aliases a
sandboxr name to the name the project's code actually reads. Values there are expanded with
`envsubst`, which substitutes `${...}` and **does not run a shell**, so a value is data and can
never be a command. [plan.json](/architecture/plan-json/)

## What a sandbox is given, and what it computes

A sandbox receives the variables that `secrets` imported, plus everything it works out for
itself. **Never put the second group in `secrets`** — put their patterns in `secrets.never`.

| The sandbox computes | Because |
|---|---|
| Database host, port, user, password, name | The database is inside the sandbox |
| Object storage endpoint, credentials, bucket names | Storage is inside the sandbox |
| Inter-service URLs | Derived from `backends.services[].port` and labels |
| Each service's own `PORT` | From its config entry |
| The environment name | The sandbox decides |
| CORS allowlists | Derived from the sandbox's own hostnames |

That last row is why a new sandbox needs no API-side configuration at all. The only external
system that has to be told about a sandbox hostname is your **identity provider**, and one
wildcard per app label covers every slug for ever.

Importing any of the above would point a sandbox at the developer's own database or at real
cloud storage, silently, with the app working perfectly. [In full](/config/secrets/).

## Where state actually lives

| Path under `SANDBOXR_HOME` | Contents |
|---|---|
| `cache/` | Database seed artifacts, content-addressed |
| `logs/<project>/<slug>/` | Per-sandbox logs — survive the container on purpose |
| `tls/` | Certificate and key |
| `state/` | Router config, dashboard session secret |
| `secrets/<project>.env` | Third-party credentials, mode 0600 |
| `build/<project>/<slug>.env` | The generated per-sandbox environment |
| `bin/` | Host-built helper binaries |

Everything *about a sandbox* lives in Docker labels rather than here, so listings cannot go
stale. [Why](/architecture/state/).

## Docker names, for reference

Derived from the project and slug, so you can find things by hand.

| Thing | Pattern | Example |
|---|---|---|
| Container | `sandboxr-<project>-<slug>` | `sandboxr-acme-feat-123` |
| Network | `sandboxr` | one, shared by everything |
| Database volume | `sandboxr-data-<project>-<slug>` | `sandboxr-data-acme-feat-123` |
| Storage volume | `sandboxr-blob-<project>-<slug>` | `sandboxr-blob-acme-feat-123` |
| Built binaries | `sandboxr-bin-<project>-<slug>` | |
| Built sites | `sandboxr-www-<project>-<slug>` | |
| Shared dependencies | `sandboxr-deps-<hash>` | keyed on the lockfile |
| Shared Go caches | `sandboxr-gocache`, `sandboxr-gomod` | |

## Setting them

**Laptop** — a shell profile, so they survive a reboot:

```bash
export SANDBOXR_PASSWORD='a long random string'
# SANDBOXR_DOMAIN defaults to sbx.lcl, which is fine locally
```

**Server** — whatever the machine already uses for service configuration:

```bash
export SANDBOXR_DOMAIN='sbx.example.com'
export SANDBOXR_ACME_EMAIL='ops@example.com'
export SANDBOXR_PASSWORD="$(openssl rand -base64 32)"
```

[The deployment guide](/server/deployment/) has the rest.
